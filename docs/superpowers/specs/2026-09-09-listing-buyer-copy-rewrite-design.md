# Listing 买家文案明确重写

状态：2026-09-09 用户已确认最小方案。2026-09-10 原商品一次真实重写及自动云保存已成功，刷新回显缺陷正在收口；精确发布和验收状态以 `JIEJING_CURRENT_EXECUTION_STATE.md` 为准。

## 问题与决定

原平板支架在真实 SaaS 页面生成时，被旧中文手改文案的英文站点校验阻断。保护手改正确，但商家没有交给 AI 重写的出口。个人 AI 已恢复，不能再归因于密钥或重复连接检测。

采用明确重写入口，而不是自动清除手改保护，也不要求商家自己翻译。默认“AI 生成 Listing 草稿”行为保持；新增“让 AI 重写买家文案”，明确说明只重写标题、卖点、描述并保留旧稿。成功后可查看重写前文案并显式恢复三个字段。

## 边界

- 同一个公司、账号、店铺及完整 Listing 项目身份。没有新商品、调研、媒体、eBay、支付或退款动作。
- 只有 `title`、`selling_points`、`description` 可由本次模型输出替换。
- 其它七个编辑字段（category/item_specifics/keywords/price/images/logistics/risk_notes）在编辑快照中原样保持；这不是把快照升级为真实商品事实。
- 当前商品事实包、来源、演练与图片权利标记、库存、发布权限不被重写模式更改。未知事实仍未知。
- 默认模式继续拒绝不合格手改文案；明确重写模式只解除三个买家文案字段的保护，不放松新文案的语言、数量及事实校验。
- 原稿保存于不可变新报告的受限快照中；失败不生成成功报告、不覆盖旧稿。已有编辑检查点和报告不删除。
- 调用期间的新编辑、跨项目切换、他端更新、超时与保存冲突继续受既有保护；不能为“跑通”自动采用他端状态或盲重试模型。

## 技术路径

复用 `POST /stores/{store}/listing-drafts/generate`，新增明确枚举 `generation_mode= rewrite_buyer_copy`；缺省保持现有模式，未知值请求前拒绝，不消费模型。

重写请求使用已有 `current_draft_fields`，传递严格白名单的十个编辑字符串及合法手改字段名。不接收或保存任意 draft 对象、秘密引用、权限、发布回执。后端对长度、类型、敏感文本和完整快照进行校验；原文仅作保留副本，不作为必须保留或真实商品事实交给模型。

同时传入生成前已保存的 `expected_base_report_id` 与 `expected_checkpoint_revision`。后端在配额/模型前核对完整身份与源水位。新报告的重写合同保留这两个非敏感锚点。现有检查点的有效 base 选择同时验证尚未采用的重写版本：冻结源或 revision 已变化的 N 仅保留为历史，不再遮盖有效 A/B 源；GET 返回有效源及同 scope 的失效重写 ID，自动采用旧 N 仍返回冲突。商家核对后可沿原有人工冲突处理继续编辑，不需要新生成或伪造事实来解锁。已采用版本按完整公司/店铺/项目身份的历史编辑回执判定，后续普通编辑不再被旧生成 revision 冻结。多份并行重写按现有时间与 ID 顺序确定有效源，不递归互相复活。商品事实保存与编辑保存共享短店铺写事务锁；读取不加写锁。后续手动编辑请求格式与旧历史默认行为不变。

新报告现有 `listing_handoff.listing_fields` 追加 `buyer_copy_rewrite` 合同，包含项目关联的安全原始编辑快照、新编辑快照及原手改字段。其它七字段逐值等于原快照。复用已有不可变报告存储和租户过滤，不新增数据库、历史中心或通用恢复 API。

前端只从合法同项目报告恢复该合同。重写前先核当前编辑云保存，拒绝未解决冲突；生成期间锁定同项目请求。成功采用与云检查点使用发起时的已知 revision 和新报告 base，CAS 冲突不能自动覆盖或重试。生成后的恢复入口只写回旧三个文案字段，走现有商家编辑保存；不恢复旧商品事实或价格。

重写不隐式提交商品资料表单；未保存的事实编辑须先完成原有保存。服务器只使用已核对来源中的商品事实与演练/权利标记。生成请求或新版本采用的响应丢失时，区分“已明确失败”和“结果尚未确认”，保留现稿并先回读项目记录，不能提示盲目重调模型。持久化前的校验必须与实际存储脱敏边界一致，不能宣称逐字保留却在落库时静默改写快照。

失败码不是“没有保存”的证据：模型校验与存储异常可能映射到同一个公开错误码。受控生成异常增加 `report_save_attempted`，仅完整失败响应明确为 `false` 时允许商家主动重试；开始调用报告保存前即置 `true`，旧响应、通用异常与截断响应均保持结果未知，不自动重调模型。生成 POST 返回的报告必须带后端已授权的公司/店铺归属，与认证 GET 一致；前端不能补造归属或放宽跨租户校验。

生成前的源读取异常是另一种明确未执行的失败：仅现有 HTTP 503、`status=blocked`、`failure_code=listing_rewrite_source_unavailable` 的完整九字段响应，且唯一 blocked_by 与其一致、model_called/usage_consumed/real_platform_writes_enabled/secret_exposed 均严格 false、report 为 null，允许商家主动再试。缺字段、额外执行阶段信息或互相矛盾的信封仍保留结果未知；不把所有 503 或单独 model_called=false 当作可安全重试。真实 HTTP 故障回归须证明任务、报告和配额未增加，页面回归须证明没有自动重试、显式第二次点击可恢复。

## 2026-09-10 刷新回显补充约束

真实原商品验收发现：认证云检查点已经保存新文案，但整页刷新时，早到的检查点先正确显示新稿，随后扩展报告恢复又显示旧缓存。不可用再生成、重存旧稿或直接修改业务数据掩盖这个问题。

- 报告中的新重写文案本身仍不等于采用成功；未采用或结果未知的报告必须继续从 `previous_fields` 安全恢复。
- 同次认证刷新中已验证、同账号/公司/店铺/完整项目身份且同 base/revision 的干净检查点，在后续报告重建草稿后仍应正确回显。不能因读取先后不同，让“已云端保存”对应旧文案。
- 不覆盖刷新期间的商家新编辑，不越过待保存、冲突、跨身份或过期响应保护。历史三个旧文案保持可查看，事实、价格、图片权利和演练边界不变。
- 保留未完成编辑只适用于当前路由指向的商品；打开商品 B 时，商品 A 的待保存内容仍归 A，不能阻止 B 的正常恢复或作为 B 的文案显示。
- 必须通过真实本地 HTTP 的整页刷新回归验证早到和晚到两种顺序；仅在手动构建草稿后强制 hydrate 的测试不足以证明此问题已修复。测试不调用真实模型，不进行生产业务写入。
