# 捷境真实商家反馈闭环设计

## 1. 背景

捷境商家工作舱已经提供流程意见入口。商家可以选择“这一步不清楚”“结果不对”或“缺一个动作”，并补充简短说明。当前前端在提交后显示“意见已提交给 JIEJING 团队”，但记录实际只写入浏览器 `localStorage`，后端和独立运营后台均无法读取。

这会造成三个直接问题：

- 页面成功提示与真实行为不一致；
- 商家换设备、清理浏览器或浏览器故障后，反馈可能永久丢失；
- 免费邀请内测即使开始，主理人也无法基于真实反馈判断产品阻塞和优先级。

本设计把现有产品改进意见升级为后端权威、租户隔离、可重试、可审计的真实反馈闭环。它服务于 eBay-first AI CEO SaaS 的内测学习，不新增通用工单系统、CRM 或 Agent 市场。

## 2. 目标

- 商家提交产品/流程意见后，后端真实接收并返回可核对的回执。
- 页面只在后端确认成功后显示“已送达”；离线或失败时展示真实状态并保留待重试记录。
- 独立运营后台可以查看聚合趋势和经过清洗的反馈内容，并完成“待处理、处理中、已解决”闭环。
- 普通商家只能访问自己公司提交的反馈状态，不能读取其他租户反馈、内部处理信息或平台级统计。
- 反馈数据不包含密码、Token、Secret、API Key、平台账号资料、原始 Prompt、模型回答或供应商诊断数据。
- 不触发 eBay OAuth、eBay 读写、付款、退款、广告、采购、改价、库存或政策修改。

## 3. 非目标

- 不把反馈系统扩展为通用客服工单、售后纠纷或买家消息系统。
- 不把“有用、没用、记住规则”等商家经营记忆在本阶段全部迁移；本阶段只处理明确的 `product_improvement` 产品/流程意见。
- 不发送邮件、短信、Slack、Webhook 或第三方通知。
- 不允许商家通过反馈触发任何经营动作或绕过确认中心。
- 不把本功能完成计入支付、eBay 正式连接、真实商家完整流程或最终商业上线分值。
- 不改变 `beta_ready`、`production_ready`、`can_accept_real_customers` 或 `public_charging_allowed` 的计算。

## 4. 方案比较

### 方案 A：后端权威反馈记录加运营闭环（采用）

新增租户隔离的数据表、认证提交接口、浏览器安全待发队列和内部运营处理视图。成功提示以服务器回执为准。

优点：修复真实产品诚信问题；内测反馈不会只留在单台设备；主理人可以持续学习和处理。缺点：需要新增 additive migration、接口、内部视图和离线重试测试。

### 方案 B：只修改提示为“已保存在本机”（拒绝）

改动最小且文案真实，但团队仍收不到反馈，无法支撑邀请内测的产品学习闭环。

### 方案 C：接入外部客服或项目管理 SaaS（拒绝）

会扩大第三方数据边界、密钥管理和供应商暴露面，也偏离当前独立运营后台优先的架构方向。

## 5. 数据模型

新增 `merchant_product_feedback` 表，SQLite 与 PostgreSQL 保持同一合同：

- `feedback_id`：不可预测的内部记录 ID；
- `company_id`、`user_id`、可空 `store_id`：租户归属；
- `feedback_type`：本阶段固定为 `product_improvement`；
- `module_key`、`reason`：受控枚举；
- `status`：`open`、`reviewing`、`resolved`；
- `idempotency_key_hash`：只存公司作用域哈希，不保存浏览器原始幂等键；
- `created_at`、`updated_at`、可空 `resolved_at`；
- `feedback_json`：经过服务端白名单、限长和脱敏后的内容。

唯一约束为 `(company_id, idempotency_key_hash)`。重复提交同一安全载荷返回原记录；相同幂等键配合不同载荷必须返回冲突，不能悄悄覆盖。

新增按公司和创建时间、状态和更新时间的索引。migration 只增加表、索引和版本记录，不删除、重写或清理现有数据。

## 6. 服务端输入合同

认证商家使用 `POST /product-feedback`。请求只接受：

- `idempotency_key`；
- `feedback_type=product_improvement`；
- `module_key`；
- `reason`：`unclear`、`wrong_result` 或 `missing_action`；
- `detail`：最多 420 个字符；
- `stage_title`：最多 160 个字符；
- 可选的 `task_id`、`report_id`、`confirmation_id`、`packet_id` 上下文编号。

服务端不得信任浏览器脱敏。它必须再次执行：

- 严格字段白名单和类型检查；
- 长度、枚举和空白规范化；
- 密码、Token、Secret、API Key、云凭证等模式脱敏；
- HTML 和控制字符处理；
- 公司作用域幂等校验；
- 共享后端 rate-limit bucket 限流，不保存原始 IP；
- 上下文编号仅作为不可信定位标签，不能作为授权、跨租户查询或执行依据。

反馈正文不得写入普通访问日志。审计日志只记录动作类型、反馈 ID、租户、状态变化和安全摘要，不复制正文。

## 7. API 与权限边界

### 7.1 商家接口

- `POST /product-feedback`：认证用户提交当前公司的反馈。
- `GET /product-feedback`：只返回当前公司最近的有限条反馈回执，包括反馈 ID、模块、原因、状态和时间；不返回内部处理备注。

未认证请求返回 401。跨租户 ID 不可枚举；普通商家不能通过 ID 读取其他公司的反馈。

### 7.2 独立运营后台

- `GET /owner/operations/feedback`：复用现有 platform-internal-admin operations detail 权限，支持状态、模块和时间筛选及有界分页。
- `POST /owner/product-feedback/review`：把 `open` 推进为 `reviewing`。
- `POST /owner/product-feedback/resolve`：把反馈推进为 `resolved`。

状态操作要求 platform internal admin，并写入审计记录。普通商家访问内部读取或处理接口必须返回 403。运营记录只显示经过清洗的短文本，不返回用户 ID、公司 ID、店铺 ID、原始幂等键、凭证或供应商诊断数据。

`platform_operations_overview()` 增加内部聚合：总反馈数、待处理数、处理中数、已解决数、按模块和原因的计数、最旧待处理时长。聚合不进入商家导航或公开 readiness。

## 8. 浏览器交互与离线恢复

现有意见入口和三种原因保持不变，不新增侧边栏模块。

提交行为改为明确的状态机：

1. `submitting`：按钮禁用并显示正在送达；
2. `delivered`：只有收到后端成功或幂等重放回执后，显示“意见已送达”；
3. `queued_local`：网络中断、超时或会话过期时，显示“已保存在本机，联网并登录后自动重试”；
4. `failed_validation`：输入被服务端拒绝时，显示可修正错误，不声称已提交。

浏览器保留一个与账号和店铺作用域绑定的有限待发队列。每条记录使用稳定幂等键；登录恢复、工作舱初始化或用户手动重试时发送。成功后从待发队列移除并保留有限的本机回执历史。

待发队列不得跨账号读取，不得包含会话令牌、模型 Key、eBay Token 或完整运行输出。达到上限时保留最新记录并明确提示，不静默无限增长。

## 9. 独立运营后台体验

在现有内部经营数据区域增加“商家产品反馈”卡片和有界明细，不创建第二套后台：

- 卡片显示 open/reviewing/resolved 数量和最突出的问题模块；
- 明细显示时间、模块、步骤、原因、清洗后的短说明和当前状态；
- 运营人员可以标记处理中或已解决；
- 无反馈时显示真实空状态；
- 平台错误、鉴权失败或读取失败时 fail closed，不回退为假数据。

该区域只在 `ops.jiejing.shop` 的 platform internal admin 会话中出现。`app.jiejing.shop` 不展示内部反馈队列、处理状态、聚合诊断或运营身份。

## 10. 安全与隐私

- 前端脱敏只是体验层；后端是最终安全边界。
- 服务端只保存完成产品改进所需的最小字段。
- 不保存原始 IP、User-Agent、Authorization header、Cookie 或第三方响应。
- 不保存 Prompt、模型回答、Listing 正文、买家信息、平台凭证或付款资料。
- 内部反馈文本按不可信输入转义，禁止 trusted HTML 注入。
- rate limit、正文上限和分页上限共同控制滥用与成本。
- feedback ID、幂等键和上下文编号都不能替代租户鉴权。
- 所有运营状态变更进入审计日志；正文不复制到审计日志。
- 读取反馈不会触发外部 API；处理反馈只更新内部状态。

## 11. 失败处理

- 数据库写入失败：返回明确错误，浏览器保留待发记录，不显示已送达。
- 响应丢失但数据库已写入：同一幂等键重试返回原回执。
- 同键异载荷：返回 409，保留原记录，不覆盖。
- 会话过期：保留队列，要求重新登录后重试，不把内容发给匿名接口。
- 服务端清洗后正文为空：允许只凭受控原因提交；原因和正文同时为空则拒绝。
- 内部运营读取失败：显示不可用状态，不把反馈内容放入错误日志。
- 回滚到旧前端后：新增表和记录保持未使用状态，不删除真实反馈。

## 12. 测试设计

按 TDD 完成以下聚焦验证：

1. SQLite 与 PostgreSQL migration 可重复执行，旧数据不受影响。
2. 认证商家可提交反馈并获得服务器回执；未认证返回 401。
3. 同一幂等键同载荷只保存一次；同键异载荷返回 409。
4. 商家只能列出本公司反馈，跨租户访问失败。
5. 普通商家访问 owner feedback 接口返回 403。
6. 内部管理员可以有审计地推进 `open -> reviewing -> resolved`，非法倒退被拒绝。
7. 服务端脱敏密码、Token、Secret、API Key 和控制字符；响应、审计及日志不泄漏原文。
8. 反馈提交 rate limit 使用共享后端 bucket，且不存原始 IP。
9. 前端只有收到服务器回执才显示已送达；离线、超时和 401 进入真实待重试状态。
10. 待发队列按账号/店铺隔离，幂等重试成功后清除，不重复创建记录。
11. 运营后台聚合、筛选、空状态、移动端布局和 HTML 转义通过。
12. 商家导航与主站不出现内部反馈队列、运营统计、供应商名称或诊断数据。

完成聚焦测试后运行秘密扫描、相关前后端回归、完整 precloud deployment gate、部署包校验和线上只读验收。

## 13. 发布与回滚

1. 先部署 additive migration、repository 和 API，再让同一版本前端开始发送；旧浏览器仍可继续本地保存。
2. staging dry-run/apply 遵循现有部署合同，不手工绕过 GitHub Actions。
3. 部署后使用有效 TLS 验证 `/health`、`/health/deep`、`/readiness/product-saas`、ops 权限和主站隔离。
4. 只使用模拟反馈做线上验收；不触发 eBay、支付或外部消息。
5. 若提交链路异常，回滚代码但保留 additive 表和已写入反馈，禁止清理真实数据。

## 14. 进度与后续顺序

本改动修复产品诚信和内测学习闭环，但不直接增加固定 100 分制得分。固定进度必须继续由真实后端、云端、支付、eBay 和商家证据计算。

本阶段完成后，下一优先级是基于后端证据增加邀请内测激活漏斗：注册、创建店铺、eBay 授权、官方数据包、首个 AI CEO 报告、确认中心决策和重复使用。该漏斗另立规格，避免把本阶段扩成新的大系统。

## 15. 完成定义

只有以下条件全部满足，才能声称“真实商家反馈闭环已完成”：

- 商家成功提示严格绑定后端回执；
- 离线、超时和会话过期不丢反馈且不虚报成功；
- 后端记录幂等、租户隔离、限流、脱敏并可审计；
- 独立运营后台可以安全查看和处理真实反馈；
- 普通商家和主站无法访问内部反馈运营数据；
- SQLite/PostgreSQL、前端状态机、权限、安全和浏览器测试通过；
- 完整部署门禁通过，部署包和 SHA256 可核验；
- 线上有效 TLS、健康、权限和主站隔离验证通过；
- 未发生真实 eBay 写入、真实收费、退款或固定进度虚增。
