# 捷境正式上线完成计划设计

日期：2026-07-27

状态：总体方案 A 已由主理人批准，等待书面规格复核

## 1. 目标

本计划把捷境从当前可用的受控私测 SaaS 推进到证据完整、可回滚、可正式接客的 eBay-first AI CEO SaaS。正式公开上线进度继续使用固定 100 分契约，不用功能数量、代码行数或主观估算替代真实上线证据。

当前证据基线为：

- 固定正式上线进度：59/100；
- 完整预云部署门禁：107/107 通过；
- `beta_ready=true`；
- `production_ready=false`；
- `can_accept_real_customers=false`；
- `public_charging_allowed=false`；
- `real_platform_writes_enabled=false`；
- eBay Token 刷新成功次数为 0；
- 当前 eBay Secret 引用数为 0。

完成目标是固定进度达到 100/100，同时每一项得分都来自后端、云端、真实账号或真实商家证据。任何证据失效都允许进度回退，不允许用手工布尔值掩盖失效状态。

## 2. 不可改变的产品与安全边界

1. 捷境保持 eBay-first AI CEO SaaS 定位，不扩展为通用 ERP、通用 Agent 市场或普通聊天机器人。
2. AI CEO 负责咨询和经营意图识别；经营任务进入工作流；实时事实来自联网或授权数据源；高风险动作进入确认中心。
3. 商家前端只使用商家语言；设置继续作为商家控制室；内部运营证据、供应商名称和诊断数据只进入独立运营后台。
4. 中国大陆正式收款以微信支付 Native 为首发路线；Stripe 只保留为未来国际支付能力，不再是大陆公开上线的必选前置条件。
5. 不使用被冻结的 eBay 账号，不重复旧 OAuth，不触发未经单独批准的真实 eBay 写入。
6. 不自动触发真实付款、退款、广告、采购、改价、库存或政策修改。
7. 密码、Token、Secret、API Key、证书私钥和原始支付回调不得进入源代码、前端、日志、测试输出、部署包或证据文档。
8. 当前脏工作区是最新进度来源。禁止 reset、clean、checkout 回退、擅自 stash、覆盖和大范围格式化。
9. `107/107` 只代表代码和部署门禁通过，不代表正式收费上线完成。

## 3. 为什么不能一次性大改

剩余工作包含四类不同责任边界：

- `codex_internal`：代码、测试、备份、监控、安全、浏览器回归和部署证据；
- `cloud_operator`：COS、CLS、通知渠道、容器重载和云端读回验证；
- `founder_external`：新的 eBay 卖家账号、真实商家招募和主体审核；
- `joint_confirmation`：真实 eBay 写入、退款执行、公开收费和正式发布。

这些工作必须按依赖关系分阶段完成。将它们放在一个大提交或一次部署中，会扩大回滚半径、混淆证据来源并增加脏工作区冲突风险。

## 4. 总体架构

计划采用六个相互隔离的工作流：

1. 大陆支付上线控制统一；
2. 备份、恢复和监控可靠性闭环；
3. 非计分生产安全加固；
4. 新 eBay 账号生产接入；
5. 真实商家经营路径验证；
6. 正式商业发布验收。

每个工作流独立拥有：

- 明确的代码和配置边界；
- 目标测试和完整门禁；
- 独立部署包及 SHA256；
- 部署前回滚点；
- 部署后健康、TLS、隔离和重启次数验证；
- 不包含 Secret 的证据摘要。

任何阶段失败时只回滚该阶段，不清理或覆盖其他已验证进度。

## 5. 阶段一：大陆支付上线控制统一

### 5.1 目标

消除旧 Stripe 优先审批包与已批准微信支付路线之间的不一致，建立单一、后端可信、面向大陆正式上线的支付状态来源。

### 5.2 设计

新增或抽取一个提供者中立的大陆支付上线状态聚合器。聚合器读取：

- 微信支付 Native 配置完整性；
- 受控真实支付验收证据；
- 签名支付与退款回调能力；
- 主动订单查询与金额核对能力；
- 额度与订阅状态持久化；
- 退款执行批准状态；
- 生产环境、公开收费开关和主理人批准包状态。

付费上线审批包、固定进度、运营后台和发布清单都读取同一聚合结果。旧 Stripe 字段只保留兼容和未来国际扩展用途，并明确标记为非大陆上线阻塞项。

### 5.3 失败行为

- 聚合失败必须降级为 blocked；
- 不能因为已有一次受控支付就打开公开收费；
- 不能因为 Stripe 未配置而阻塞大陆微信支付路线；
- 不能因为微信支付技术路径完成而自动批准退款或公开收费。

### 5.4 验收

- 主序列中不再出现 `stripe_live_cutover`；
- 大陆正式路线明确返回 `wechat_pay_native`；
- Stripe 被标记为未来国际路线；
- `public_charging_allowed=false` 和 `charge_now_allowed=false` 保持不变；
- 支付、运营后台、固定进度、Secret Scan 和 107 项门禁全部通过；
- 本阶段不调用任何真实支付 API。

## 6. 阶段二：可靠性证据闭环

### 6.1 备份与恢复

执行顺序固定为：

1. 只读检查当前备份配置和过期原因；
2. 创建生产预备数据库的一致性备份；
3. 将加密分片上传到 COS；
4. 全量回读并重组；
5. 校验源文件与重组文件 SHA256；
6. 使用无网络、无持久卷的隔离 PostgreSQL 容器恢复；
7. 核对核心表结构和行数；
8. 只记录布尔值、计数、大小、哈希和证据编号；
9. 顺序重载 API 与 Worker；
10. 重新验证有效 TLS 健康检查和运营后台隔离。

备份或恢复任何一步失败都不得刷新证据时间，不得获得对应 3 分。

### 6.2 被动提供者监控

继续使用已批准的 Worker 原生被动调度器：

- 每五分钟读取已有真实经营遥测；
- 不主动调用模型、搜索、媒体、支付或 eBay；
- 多 Worker 通过数据库租约保证每个周期只有一次计算；
- 无真实样本必须显示 `insufficient_data`，不能显示 healthy；
- 每次评估最多上传一个隐私安全的聚合 CLS 事件；
- 延迟和成本告警必须通过云端读回验证，而非手工布尔值；
- Probe 事件必须被告警查询明确排除；
- 不发送测试通知。

### 6.3 云配置

CLS 只增加告警所需的最小键值索引，不启用全文索引。通知渠道优先复用现有内部告警路线，不输出通知渠道标识。

每日成本告警不设置虚假的系统默认值。先根据套餐收入、模型与媒体成本、目标毛利和私测规模生成建议，再由主理人确认 warning 与 critical 两个 minor-unit 阈值，且 critical 必须大于 warning。

### 6.4 验收

- COS 在线证据新鲜且恢复演练通过；
- CLS 控制面和安全合成写入证据新鲜；
- 被动调度器和聚合导出证据新鲜；
- 两个告警均通过读取验证；
- 成本预算合法；
- 无样本状态仍诚实显示数据不足；
- 可靠性得分从 13/20 提升到 20/20；
- 固定总进度预计从 59/100 提升到 66/100。

## 7. 阶段三：非计分生产安全加固

该阶段不改变固定安全 10/10 得分，但降低正式接客风险。

### 7.1 CSP

逐页盘点内联脚本和样式，将业务脚本迁移到静态文件或安全 nonce/hash 机制。只有所有主站页面和登录流程回归通过后，才移除 `unsafe-inline`。

### 7.2 HSTS

先完成主域名和全部受管子域名 TLS 清单。仅在确认所有需要保留的子域名都支持有效 HTTPS 后启用短周期 HSTS；观察无误后再考虑延长，不直接启用不可逆的 preload。

### 7.3 会话与服务运行

- 继续强化短访问令牌、轮换刷新令牌和服务端撤销；
- 确认浏览器不持久化公开 Bearer Token；
- 将开发型线程服务器迁移到可控并发、超时和优雅关停的生产服务模型；
- 保持运营后台更严格的 CSP、no-store 和身份隔离。

### 7.4 验收

- XSS、权限、会话撤销、CSRF/回调、限流和 Secret Scan 通过；
- 主站与运营后台桌面和移动端无回归；
- 有效 TLS、HTTP 到 HTTPS 跳转和后台隔离通过；
- 107 项门禁保持全绿。

## 8. 阶段四：新 eBay 账号生产接入

### 8.1 前置条件

只接受新的、状态正常的 eBay 卖家账号。被冻结账号、旧测试商品、旧 SKU、旧素材和旧 OAuth 记录不得复用。

### 8.2 只读接入顺序

1. 执行账号和凭证只读预检；
2. 主理人明确登录新的卖家账号；
3. 只执行一次经过批准的 OAuth；
4. 凭证只写入 Vault/后端 Secret 引用；
5. 生成官方 API 只读数据包；
6. 验证店铺同步可见性；
7. 等待并验证至少一次 Token 自动刷新成功；
8. 检查健康、过期和撤销行为。

完成这些步骤最多取得 eBay 类别前 16 分，不触发真实刊登。

### 8.3 最后低风险验证

最后 4 分需要一个全新的合规商品、SKU 和素材。任何真实刊登、修改或清理都必须进入确认中心，由主理人单独批准。超时后先查询平台状态，禁止盲目重试。

## 9. 阶段五：真实商家经营路径验证

### 9.1 计分规则

固定要求同时满足：

- 至少 3 个相互独立的真实商家公司；
- 至少 20 条完成决策的真实 `product_workflow` 路径。

每条路径必须包含任务成功、运行报告、确认项，以及商家在确认中心作出的批准、拒绝或要求修改决定。合成账号、演练和不完整路径不计分。

### 9.2 隐私边界

运营后台只显示聚合计数和下一行动，不返回邮箱、公司名、用户 ID、店铺 ID、Prompt、报告内容、Secret 或供应商名称。

### 9.3 验收

- 真实独立商家数不少于 3；
- 合格经营路径不少于 20；
- 合成账号排除测试通过；
- 商家无法访问内部进度和诊断接口；
- 固定总进度预计从 86/100 提升到 91/100。

## 10. 阶段六：正式商业发布验收

正式上线必须使用独立 production 环境，不能把当前 staging 原地切换成 production。

最终验收包括：

- 微信支付签名回调、主动查询、金额核对和额度发放；
- 人工批准的受控全额退款证明；
- 客服、退款政策、隐私、条款和风险披露页面；
- 支付对账、异常恢复和退款期间回调持续可达；
- 新部署包、数据库备份、Secret Scan、回滚包和浏览器验收；
- 最终无真实扣费上线演练；
- 主理人公开收费批准；
- 主理人正式发布批准。

只有这些条件全部满足，后端才能把 `production_ready`、`can_accept_real_customers` 和公开收费状态推进到正式状态。单一开关、受控支付证明或健康的 staging 都不足以批准上线。

## 11. 固定进度路径

预期进度路径如下：

- 当前：59/100；
- 备份与监控完成：66/100；
- eBay 生产接入全部完成：86/100；
- 真实商家验证完成：91/100；
- 退款、最终商业演练和主理人批准完成：100/100。

支付控制纠偏和安全加固本身可能不增加分数，但它们是避免错误上线和后续返工的必要条件。

## 12. 发布与回滚策略

1. 每个阶段使用小范围提交，不混入无关格式化或清理。
2. 先运行目标测试，再运行 Secret Scan 和完整 107 项门禁。
3. 每次部署生成新包、清单和独立 SHA256。
4. 部署前保存数据库、环境配置和应用镜像回滚点，不输出 Secret。
5. API 与 Worker 顺序更新，避免同时失去服务与队列处理能力。
6. 部署后使用正常证书校验验证 `/health`、`/health/deep` 和 `/readiness/product-saas`。
7. 验证 `ops.jiejing.shop` 权限、主站隔离、DNS、有效 TLS 和容器重启次数。
8. 任何关键验证失败立即保持公开收费和平台写入关闭，并回滚本阶段。

## 13. 测试策略

每个阶段至少覆盖：

- 单元和契约测试；
- SQLite 与 PostgreSQL 兼容性；
- 租户和权限隔离；
- Secret 与敏感数据泄漏扫描；
- 重放、重复、延迟、乱序和部分失败；
- 桌面、移动端和未认证浏览器流程；
- 目标模块回归；
- 完整 107 项门禁；
- 部署后线上只读验收。

测试失败时不得通过修改进度文件、降低阈值或跳过检查来获得通过。

## 14. 主理人介入点

普通代码、测试、只读检查和本地打包不需要逐项确认。只有以下节点暂停并请求主理人决定：

1. 确认监控成本 warning 与 critical 阈值；
2. 登录新的 eBay 卖家账号并批准一次 OAuth；
3. 批准任何真实 eBay 写入或清理；
4. 批准受控真实退款执行；
5. 批准公开收费；
6. 批准正式发布。

## 15. 完成定义

项目只有在以下事实同时成立时才称为正式完成：

- 固定上线进度为 100/100；
- 完整门禁通过；
- production 环境、备份、恢复、监控和告警证据新鲜；
- 新 eBay 账号的授权、刷新、同步和受控验证完成；
- 真实商家和经营路径阈值完成；
- 微信支付、退款、对账、支持和异常恢复完成；
- 运营后台与商家前端保持隔离；
- 所有 Secret 留在后端边界；
- 主理人已分别批准公开收费和正式发布。

在此之前，捷境继续诚实标记为私测可用、正式公开上线受阻。
