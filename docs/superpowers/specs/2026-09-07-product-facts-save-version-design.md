# 商品资料保存版本修复

2026-09-07。范围：已定位的 A→B→A 保存/刷新不一致，用户已授权继续局部流程修复。
当前执行状态仍以 `docs/JIEJING_CURRENT_EXECUTION_STATE.md` 为唯一索引。

## 商家行为与非目标

同一商品保存 A、修改为 B、再改回 A，应留下第三次保存的不可变记录，刷新采用第三次 A。
网络重试复用同一动作，不重复创建记录；旧动作迟到不得覆盖当前版本。
不更改套餐、权限、事实审核、产品结构或 UI 风格，不调用模型、FAL、eBay、资金能力或生产服务。

## 方案选择

不刷新旧报告时间：这样会让网络重试把过期资料变成最新。
不把每次请求都当新保存：这样会重复留档，也无法阻止迟到请求。
采用独立动作编号和观察版本校验；复用现有 tasks/reports，暂不增加表或迁移。

POST `/stores/:id/product-facts` 新增 `save_context`：

- `contract_version=merchant_product_fact_save_v1`
- `mutation_id`：8–160 字符的受限 ASCII 标识；独立于内容。
- `expected_fact_report_id`：商家当前看到的事实版本，首次保存可为空。

指纹绑定当前用户、公司、店铺、完整三字段项目身份、规范化事实与保存上下文。
事务先检查精确动作重放，再检查观察版本。改变同动作内容或依据版本返回 409。
成功创建新 task/report，不覆盖旧记录；响应包含原回执及当前报告 ID / `is_current`。
历史回执仍可重放，但 `is_current=false` 时前端不得宣称当前资料保存成功。

## 并发、排序和兼容

SQLite 用立即写事务；PostgreSQL 锁同店铺行。图片提取独立事实 writer 也参与同一锁。
报告保存的实际新时间至少跨过已有同项目主要报告 1 毫秒，兼容前端毫秒排序；不改旧时间。
旧客户端缺少动作信息时不能区分新保存与迟到重试：未升级项目保留原连续去重，命中过时旧记录返回 409；
项目已有新合同记录后，旧客户端写入一律要求刷新升级，不能覆盖新合同版本。
兼容旧 digest 时必须重新验证完整项目身份，不能仅凭项目 key 跨来源或候选复用。

## 前端与失败处理

两个入口共同使用保存上下文。未完成的相同内容重试保留原动作及观察版本，成功后释放动作。
本机生成的保存时间不参与内容相等比较；修改内容、切账号/店铺/项目必须是新动作。
失败和 409 保留本页资料，不自动重发覆盖新版本；仅接受当前作用域的响应。
已有手改保护与迟到响应保护保持。账号登录与真实平台资格无关，不作为本地保存前提。

本地草稿快照保留观察到的事实报告 ID；显式空版本也不能借用后来到达的报告 ID。
恢复本地未保存草稿及查找其后台时间基准均匹配完整项目三字段；显式空来源或候选是精确值，
不能作为通配接纳另一来源/候选的缓存或报告。相同完整身份的本地手改继续保留。
完整页面验收发现普通手工事实独立存在时不能从云端恢复：只补已有恢复入口的 facts-only fallback，
仅接受已保存、已认证、完整项目身份的商品事实；不冒充图片识别或已生成 Listing。
恢复后仍需生成/审核买家文案，保留原有 vision/Listing/market 分支与跨账号店铺隔离。
SQLite 读取主要报告按时间点而非带时区字符串排序；PostgreSQL 原 timestamptz 排序不变。

## 验证顺序

1. 原真实 HTTP ABA 故障转正式 RED，再实现最小修复。
2. 精确重放、修改动作、并发 CAS、完整身份/权限、旧客户端和事务回滚逐项验证。
3. 同毫秒/时间回退排序与事实 writer 交替；旧 Listing base 合同不变。
4. 两入口实际 DOM 点击/输入、失败重试、历史回执、冲突不覆盖；补完整 app→本地 HTTP 组合验收。
5. 独立审查及真实本机 PostgreSQL 定向复核；通过后与上批修复统一冻结。
6. 新候选完整门禁/CI/包/dry-run 是后续发布步骤；本地通过不等于部署或真实商家验收。
