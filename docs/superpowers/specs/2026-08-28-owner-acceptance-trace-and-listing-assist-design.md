# 捷境代操作验收留痕与 Listing 辅助设计

日期：2026-08-28  
状态：用户已确认产品方向，等待规格复核后进入实施计划

## 1. 背景与目标

本轮真实演练由 Codex 代替项目所有者在捷境内操作。Codex 是验收执行者，不是捷境面向商家的产品依赖。项目所有者登录自己的捷境账号后，应当能够回到各业务页面查看这次演练真实产生的业务记录，并能从“工作记录”定位到对应记录。

本设计不新增一张笼统的“发布回执”，也不把所有业务数据复制到第二套记录系统。

目标是：

1. AI CEO 对话、市场调研、商品资料、Listing、素材、客服、确认和平台执行均在各自业务页面持久化并可复查。
2. “工作记录”只提供当前商品项目的统一索引、时间关系和跳转入口。
3. 项目所有者的验收账号额外显示 Codex 代操作痕迹；普通商家不看到内部验收信息。
4. 普通商家不需要 Codex 接管电脑，也不需要打开 eBay 网页手工填写普通 Listing。

## 2. 用户与权限边界

### 2.1 普通商家视图

普通商家只能看到自己公司、店铺和商品项目下的业务记录：

- AI CEO 历史对话；
- 市场调研和其他业务报告；
- 商品事实、来源和缺失字段；
- Listing 草稿及版本；
- 素材生成任务、结果、审核状态和素材点变化；
- 买家消息、AI 建议回复、人工修改和发送状态；
- 与自己动作相关的确认单和平台执行结果。

普通商家不显示 Codex、内部测试步骤、模型密钥、平台凭证、原始 Token、供应商 Secret 或跨租户记录。

### 2.2 项目所有者验收视图

项目所有者的指定验收账号可以额外查看“代操作验收痕迹”，用于回答：谁在什么时候通过捷境做了什么、产生了哪个业务对象、结果如何、失败后停在哪里。

该能力通过后端权限或明确的所有者验收标记控制，不能通过前端隐藏按钮或邮箱硬编码实现。验收痕迹可以包含关联 ID、时间、步骤、状态和脱敏错误，但不得包含 Secret 原值。

验收视图是现有业务记录的索引，不是另一份可独立修改的业务数据副本。

## 3. 业务记录归属

| 记录 | 主页面 | 必须保留的内容 |
| --- | --- | --- |
| AI CEO 对话 | AI CEO | 用户消息、AI 回复、时间、关联商品项目、报告跳转 |
| 市场调研 | 市场调研/工作记录 | 报告版本、结论、来源、生成时间、关联商品项目 |
| 商品资料 | Listing 商品资料模块 | 来源、字段值、事实/建议属性、缺失项、修改时间 |
| Listing | Listing | 草稿版本、字段变更、校验结果、当前状态 |
| 素材 | 素材工坊 | 输入来源、生成任务、结果、审核、素材点结算、Listing 写回 |
| 客服 | 客服 | 买家原消息、AI 建议、人工修改、是否已发送、平台结果 |
| 高风险确认 | 确认中心 | 动作摘要、确认状态、确认人、关联项目、有效期 |
| 平台执行 | 工作记录/对应业务页 | 请求类型、成功或失败、脱敏平台错误、Offer/Listing 等关联 ID |

“工作记录”默认按当前商品项目展示上述记录的摘要和跳转，不承担业务内容编辑。

## 4. Listing 的正确生成方式

商家不需要 Codex，也不应该被要求去 eBay 手工填写普通 Listing。捷境承担 Listing 的生成、预填、校验和平台 API 交接。

### 4.1 商家输入

有货源商家提供以下一种或多种资料：

- 真实供应商商品链接；
- 自有商品照片；
- 规格表或包装信息；
- 既有商品资料。

无货源商家可以先让 AI CEO 做市场调研和选品，但在取得真实货源事实前只能停在“待补商品资料”，不能生成可诚实发布的最终商品。

### 4.2 捷境自动处理

捷境应自动完成：

1. 从链接、图片和文本提取结构化商品事实；
2. 对每个字段记录来源，并区分“已确认事实”和“AI 建议”；
3. 根据 eBay 类目要求生成字段清单和 item specifics；
4. 从已连接店铺预填库存地点、付款、退货和履约政策；
5. 生成标题、描述、定价建议和 Listing 草稿；
6. 执行必填字段、来源、图片权利和平台预检；
7. 保存草稿、生成确认单，并在获得动作时确认后调用 eBay API。

### 4.3 商家补充与审核

AI 无法可靠判断的事实不得编造。Listing 页面提供独立的“商品资料”模块，把字段分为：

- 已从来源提取：商家可核对或修改；
- AI 建议：采用前必须由商家确认；
- 必须补充：缺失时阻止进入发布确认；
- 可选优化：不阻断草稿。

商家在这个模块一次性补齐资料，AI CEO 对话只负责解释和引导，不通过反复追问代替表单。商家随后在捷境内预览、编辑和确认 Listing。

## 5. 客服记录边界

客服页面必须区分：

- 买家真实消息；
- AI 生成的建议回复；
- 商家修改后的待发送回复；
- 已通过平台发送的回复；
- 仅用于验收的模拟回复。

建议回复和模拟记录不得显示成已经发送。涉及退款、赔付、折扣、改价或其他敏感承诺时，继续使用动作时确认。

## 6. 数据关联与一致性

各页面使用同一组后端业务对象，不建立平行真相。至少应支持以下关联键：

- company_id；
- store_id；
- listing_project_id；
- run_id / task_id；
- conversation_id / turn_id；
- report_id；
- product_fact_packet_id；
- listing_version_id；
- media_job_id；
- customer_service_thread_id；
- confirmation_id；
- execution_id。

旧记录缺少 listing_project_id 时，只允许通过明确、可验证的来源报告或 Listing 关系回填；不得仅按商品名称猜测归属。

## 7. 验收标准

1. 项目所有者重新登录后，能够在 AI CEO 页面看到本轮演练的对话。
2. 能在对应业务页面看到市场报告、商品资料、Listing 草稿/版本、素材生成与审核记录。
3. 如执行过客服演练，能够区分真实消息、建议回复、模拟和已发送状态。
4. “工作记录”能够按商品项目列出这些记录并跳转到原页面，不复制一份可编辑内容。
5. 项目所有者能看到 Codex 代操作步骤的脱敏验收痕迹；普通商家账号看不到该能力。
6. 跨公司、跨店铺和跨商品项目数据不能串联或泄露。
7. 任何密钥、Token、Secret 和原始平台凭证均不进入前端、日志或验收记录。
8. eBay 账号受限时，既有对话、报告、商品、Listing、素材和客服流程仍可继续；仅真实平台写入保持受限。
9. 普通商家仅使用捷境网站即可完成资料输入、AI 生成、补充、审核、草稿保存和发布确认，不依赖 Codex 或手工 eBay Listing 表单。

## 8. 非目标

- 不为所有商家开放内部测试和模型调用明细。
- 不把 Codex 做成捷境的客户侧运行组件。
- 不因本次验收新增第二套报告、Listing 或素材数据。
- 不在没有商品事实和图片权利证据时让 AI 编造可发布商品。
- 不因 eBay 账号限制而重复 OAuth、重复发布或隐藏失败状态。
