# AI CEO 开放域对话与商家货源接力设计

日期：2026-08-24  
状态：方案 B2 与货源边界已由项目负责人确认；Seller Hub 人工接力方案待确认
范围：`app.jiejing.shop` 的 AI CEO 对话内核、通用问题研究、模型分层、商家商品事实采集、市场调研到 Listing 的接力

## 1. 已确认产品决定

1. 捷境继续是 eBay-first AI CEO SaaS，不改造成通用 ERP、Agent 市场或货源交易平台。
2. AI CEO 必须具备开放域普通助手能力。天气、实时股票、公司基本面、写作、解释和其他项目外问题都应先正确回答，不能被强行导向 eBay 工作流。
3. 当前回答质量的首要问题是对话编排，而不是简单归因于 DeepSeek 模型能力。现有前后端重复意图推断、关键词路由、最近八轮平铺历史和不完整任务状态会污染模型输入。
4. 采用方案 B2：开放域对话内核、结构化任务状态、动态工具调用、相关上下文检索、答案验证和 DeepSeek 模型分层。
5. 捷境不自营商品、不囤货、不采购、不代替商家建立供应关系，也不建设“捷境已核验货源池”。
6. 无货源商家由 AI CEO 完成市场调研和候选商品推荐，商家自行寻找真实货源；找到后把链接、图片或规格交给捷境。
7. 已有货源商家直接提交链接、图片或规格，不需要先做选品。
8. 两类商家在获得真实货源后汇入同一条商品事实与 Listing 流程。商家不应打开 eBay 网页手工填写 Listing。

## 2. 需要解决的真实问题

### 2.1 开放域对话失真

当前 AI CEO 同一条消息可能同时经过前端关键词意图、后端路由、实时请求分类、历史跟随判断、质量修复和前端任务卡投影。典型后果包括：

- 普通问题被误认为 eBay 经营任务；
- 否定句仍触发素材、付款或发布路径；
- “它”“继续分析”“刚才那家公司”等跟随问题丢失实体；
- 天气、实时股价或公司基本面没有拿到合适数据就开始作答；
- 模型给出正确文字，但页面状态、报告或 Listing 入口与回答矛盾；
- 模型连接 fallback 只处理瞬时失败，不能按任务复杂度主动提高推理能力。

### 2.2 货源与 Listing 责任不清

商家容易把“AI 推荐了商品”理解成“已经有可销售货源”，也容易误以为必须亲自填写全部 eBay 字段。捷境必须清楚区分：

- 市场机会：说明什么可能值得卖；
- 商品事实：说明商家实际准备销售的具体商品是什么；
- Listing 建议：捷境依据事实生成的买家文案、类目和字段；
- 最终决定：商家对售价、库存、履约和发布负责并在高风险动作前确认。

## 3. 非目标

- 不承诺 AI 真正“无所不知”；目标是对开放域问题尽量正确回答，并在需要最新数据或证据时自动研究、在证据不足时诚实说明。
- 不为每一种问题编写一个关键词分支。
- 不建设供应商市场、代采购、代付款、仓储、货代或供应链金融。
- 不从公开供应商网页推断实时库存、最终价格、发货地、图片授权或履约承诺。
- 不让无货源市场报告直接成为可发布 Listing。
- 不宣称 Inventory API 未发布 Offer 可以在 Seller Hub 编辑，也不建设不可靠的 eBay/Jiejing 草稿双向同步。
- 不在本设计中开启公开收费、广义 eBay 写入或未发布草稿开关。
- 不重复 eBay OAuth、支付、退款、旧手机壳或历史发布验证。

## 4. 开放域对话内核

用户始终只面对一个 AI CEO 对话框。后端按以下循环处理每一轮：

`理解问题 -> 建立结构化计划 -> 选择模型与工具 -> 执行只读研究 -> 更新工作状态 -> 生成答案 -> 验证答案 -> 必要时修复`

### 4.1 单一后端权威规划器

前端只负责采集消息和渲染后端结果，不再自行决定权威意图、模型档位或业务工件。后端首先生成 `ai_ceo_turn_plan_v1`：

- `response_mode`：`direct_answer`、`research_answer`、`jiejing_workflow` 或 `confirmation_required`；
- `topic` 与 `entities`：当前主题、公司、股票代码、地点、商品、报告等；
- `freshness_required`：是否必须获取当前数据；
- `research_depth`：`none`、`quick` 或 `deep`；
- `required_tools`：模型请求的只读工具；
- `workflow_target`：只有经营任务才填写；
- `risk_level` 与 `confirmation_required`；
- `model_tier`：`fast`、`thinking` 或 `pro`；
- `continuation_key`：本轮延续的主题或经营工件；
- `secret_exposed=false`。

规划器可以由模型给出候选计划，但所有工具参数、租户边界和高风险动作必须由后端确定性校验。模型不能自行授予真实写入权限。

### 4.2 开放工具注册表

工具不是固定问题菜单，而是一组可扩展能力。首版至少包括：

- 当前时间与日期；
- 天气；
- 实时行情；
- 公司基本面研究，包括财报、监管文件、新闻和行情；
- 通用网页搜索；
- eBay 官方店铺、政策、类目、Listing 与市场数据；
- 捷境内部报告、商品事实、Listing、素材和确认记录。

模型可在一轮中选择零个、一个或多个只读工具，并依据工具结果继续研究。工具循环必须有步骤、时延和费用上限，不能无限执行。真实发布、改价、库存、退款、广告、采购付款、政策修改和敏感承诺不属于自动只读工具。

### 4.3 模型分层

- `fast`：DeepSeek V4 Flash 非思考模式，用于简单咨询、改写、翻译和明确事实解释；
- `thinking`：DeepSeek V4 Flash 思考模式，用于需要多步推理但来源规模较小的问题；
- `pro`：DeepSeek V4 Pro 或同等级强模型，用于复杂公司基本面、跨来源市场调研、商品事实冲突修复和 Listing 结构化生成；
- 临时连接错误的 fallback 与任务复杂度升级必须分开记录，不能混为同一种重试；
- 商家 BYOK 保持原有账户/店铺作用域，不允许前端拿到密钥。若 BYOK 模型不支持所需能力，页面应说明能力缺口或使用已获授权的平台模型，不能静默更换计费责任。

模型升级由任务复杂度、来源数量、上一轮质量和不确定性决定，不按“天气、股票、eBay”等固定主题决定。

### 4.4 工作状态与相关上下文

新增 `ai_ceo_working_state_v1`，至少保存：

- 当前主题和实体；
- 用户目标与约束；
- 已确认事实、推断和未知项；
- 已调用工具及安全摘要；
- 当前报告、商品或 Listing 的稳定 ID；
- 待办步骤和阻断项；
- 上次答案的证据新鲜度；
- 是否属于普通咨询或经营工作流。

模型上下文由当前消息、工作状态、语义相关历史和必要业务工件组成。最近八轮原始对话只能作为辅助，不能继续作为唯一记忆机制。旧商品、旧报告和无关长答案不得因为时间较近而压过当前任务。

### 4.5 答案验证

生成后至少检查：

1. 是否直接回答用户问题；
2. 当前数据是否有来源和时间；
3. 引用是否支持结论；
4. 是否把推断写成事实；
5. 是否错误创建经营任务；
6. 是否丢失当前实体或商品；
7. 是否越过确认边界；
8. 是否出现实现词、秘密或不应展示的内部状态。

验证失败时允许一次定向修复；仍失败则返回最窄、可理解的缺口，不能用错误答案冒充完成。

## 5. 商家货源模式

### 5.1 无货源：先做市场调研

AI CEO 可以根据商家的市场、预算、商品边界和风险偏好，生成 2 至 4 个候选商品及需求、竞争、价格带、风险和取证入口。此时工件状态固定为：

- `source_mode=merchant_has_no_source`；
- `artifact_type=ai_ceo.market_research`；
- `source_fact_status=not_provided`；
- `listing_import_ready=false`；
- `blocked_by` 包含 `merchant_product_source_required`；
- 商家下一步文案为“找到货源后，把链接、照片或规格发给我”。

市场调研不得编造供应商、库存、材质、尺寸、重量、成本、品牌、MPN、发货地、物流或图片权利，也不得把候选商品直接变成可发布 Listing。为避免商家找到货源后从头开始，允许沿用现有 `ai_ceo_candidate_report_to_blocked_listing_draft_v1` 桥接创建一个明确标记为“等待真实商品事实”的内部 Listing 工作区；它只能承接选品结论和继续收集来源，不能被描述为可发布、不能进入 eBay 写入。

### 5.2 已有货源：直接采集商品事实

商家可以提供以下任一种输入：

- 真实供应商商品链接；
- 自有商品照片与规格；
- 供应商报价单、规格表或沟通截图；
- 已有 SKU 商品资料。

捷境建立 `merchant_product_fact_packet_v1`，将字段分为：

- `source_confirmed_facts`：来源中可直接确认的事实；
- `merchant_confirmed_facts`：商家明确确认的库存、成本、发货和权利事实；
- `derived_listing_suggestions`：AI 生成但需要审核的标题、卖点、类目、属性和售价建议；
- `unknown_facts`：仍缺失且会影响真实性或履约的字段；
- `source_records`：链接、图片、规格或沟通证据；
- `listing_readiness` 与 `blocked_by`；
- `secret_exposed=false`。

### 5.3 两条路径汇合

无货源商家找到真实货源后，提交来源并切换为 `merchant_source_supplied`，随后与已有货源商家走完全相同的商品事实流程。不会重新从选品第一步开始。

## 6. Listing 由谁填写

结论：Listing 由捷境生成和预填，商家不去 eBay 手工填写。

捷境自动完成：

- 从链接、图片和规格中提取商品事实；
- 只追问无法安全确认的关键字段；
- 选择 eBay 类目；
- 生成标题、卖点、描述和 Item specifics；
- 从官方账号数据包预填 inventory location、fulfillment policy、payment policy 和 return policy；
- 根据成本、运费和费用提供售价与利润建议；
- 生成素材需求并执行事实、图片权利和人工审核；
- 执行 Listing 完整性、政策和重复项预检；
- 在捷境内展示完整草稿供商家审核；
- 满足条件后保存未发布 eBay 草稿；
- 最终公开发布前请求动作时确认。

商家只需负责或确认无法由 AI 诚实推断的事实：

- 实际销售版本、SKU、品牌、MPN 和 condition；
- 真实成本、库存或供货能力；
- 实际发货地、处理时间、运费和履约方式；
- 材质、尺寸、重量和包装；
- 图片商业使用权；
- 最终售价、刊登数量和公开发布决定。

这些问题优先以对话中的小批量补问呈现，不把一张复杂 eBay 表单原样推给新手商家。设置继续作为账号、模型、店铺政策和高级控制中心。

### 6.1 商家想自己修改时

捷境提供两种明确互斥的编辑模式。

#### 模式 A：继续在捷境编辑，默认推荐

- AI 生成的标题、卖点、描述、类目、Item specifics、价格建议和物流字段都可以在捷境逐项编辑；
- 每个字段区分“来源事实”“商家填写”“AI 建议”和“账号政策预填”；
- 商家可以直接修改、接受建议或要求 AI 重写；
- 捷境草稿保持权威，保存 eBay 未发布 Offer 后的后续修改继续通过 Inventory API 更新；
- `updateOffer` 是整份覆盖，后端必须先读取权威草稿并发送完整字段，不能只提交一个局部字段；
- 商家无需打开 Seller Hub。

#### 模式 B：转到 eBay Seller Hub 自己补充，可选逃生口

eBay 官方明确区分 Seller Hub Draft 与 Inventory API Offer。通过 Inventory API 创建的 Listing/Offer 不能在 Seller Hub 或其他刊登工具中编辑；修改必须继续走 Inventory API。因此现有 `save_ebay_listing_draft` 适配器不能被描述为“保存后去 eBay 网页继续填”。

如果商家明确选择“转到 eBay 自己补充”，捷境应使用独立的 Seller Hub Draft 接力适配器：

- 使用 Sell Feed API 的 `FX_LISTING` 与 Draft Action（Create new drafts）创建真正的 Seller Hub Draft；
- 这是一次真实但不公开的平台写入，执行前必须显示将要转交的 SKU、字段快照和目标账号，并获得动作时确认；
- 创建成功后返回 Seller Hub Draft 入口、Feed task ID 的安全引用和本次字段快照，不回传 OAuth token；
- 同一 SKU 不得同时维护一个可继续更新的 Inventory API Offer 和一个 Seller Hub Draft；
- 转交后设置 `edit_owner=ebay_seller_hub`，捷境草稿进入只读快照或“等待 eBay 对账”，停止自动覆盖；
- 这是一条单向人工接力，不承诺把 Seller Hub Draft 的每个修改实时同步回捷境；
- 商家在 eBay 完成或发布后，可在捷境点击“我已在 eBay 完成”，捷境按稳定 SKU、账号和时间窗执行只读对账；
- 只有读到匹配的 Item ID/Listing 状态后，捷境才记录发布成功；未找到时保持 `external_handoff_pending`，不得冒充完成；
- Seller Hub Draft 有平台保留期限，界面必须展示 eBay 返回或官方规则中的到期提示。

默认仍推荐模式 A，因为它能保持捷境审计、事实门禁和流程连续性。模式 B 只服务于商家确实希望使用 eBay 原生界面补充特殊字段的情况。

## 7. 商家界面

- 保持一个主要输入框，不增加“通用聊天/天气/股票/eBay”模式选择器；
- 普通咨询直接展示回答、来源和数据时间，不展示任务卡；
- 只有形成市场报告、商品事实包、Listing、素材任务或确认事项时才展示业务工件；
- 市场报告明确展示“推荐卖什么”与“还没有真实货源”；
- 商品事实包明确区分“来源已确认”“商家已确认”“AI 建议”“仍待补充”；
- Listing 页面默认展示捷境已填内容，商家只处理缺口和审核；
- Listing 页面提供“我来修改”和“转到 eBay 自己补充”；后者必须解释这是单向接力而不是同步编辑；
- 页面不得出现 packet、provider、preflight、worker、Vault、model tier 等内部词。

## 8. 审计、安全与计费

- 每轮记录规划结果、工具类型、模型档位、来源数量、时延、质量结果和最终状态，但不保存秘密或原始凭证；
- 普通聊天不写长期经营记忆；只有明确商家规则和经营工件进入永久记录；
- 工具调用全部按 company、account、store 和 user 作用域隔离；
- 实时搜索和模型调用按套餐计量，但商家只看到可理解的用量，不看到密钥或内部路由；
- 失败在模型调用前则不消耗模型次数；模型或外部研究已经真实执行时必须诚实记录用量；
- 所有真实平台写入继续由后端确定性门禁与确认中心控制。

## 9. 实现顺序

### 阶段一：开放域对话内核

1. 建立失败回归用例；
2. 新增结构化 turn plan 与 working state；
3. 后端成为唯一权威路由，前端停止独立创建权威意图；
4. 建立工具注册表和受限多步只读循环；
5. 实现模型复杂度分层；
6. 实现答案验证和定向修复；
7. 保持现有报告、审计、租户和秘密边界。

### 阶段二：商家货源接力

1. 固化无货源市场报告的 `merchant_product_source_required` 阻断；
2. 保留被事实阻断的内部 Listing 工作区，仅用于连续接收后续来源；
3. 建立商品事实包；
4. 支持链接、照片、规格和供应商回复的事实提取；
5. 缺口按影响排序并分批询问；
6. 将事实包映射到 Listing；
7. 保持已存在的账号级 eBay 政策预填；
8. 不重复选品或 OAuth。

### 阶段三：生产验收

1. 本地专项测试；
2. JavaScript 语法检查、秘密扫描和完整部署门禁；
3. 生产 dry-run；
4. 获得部署动作确认后发布；
5. 使用 Chrome 登录态回归开放域问题和两类商家流程；
6. 核验 `/health`、`/health/deep`、`/readiness/product-saas` 与 ops 隔离；
7. 不把 HTTP 200 等同于公开收费或真实平台写入就绪。

## 10. 首批回归矩阵

1. “上海明天天气怎么样”调用天气/实时研究，不创建 eBay 任务。
2. “英伟达现在股价怎么样”获取带时间的行情，不生成 Listing。
3. “AAOI 基本面有什么问题”执行深度公司研究，区分财报事实、新闻和分析判断。
4. 紧接着问“它为什么最近波动这么大”仍保持 AAOI 实体。
5. 普通写作或概念问题直接回答，不联网时也不进入经营工作流。
6. “帮我找适合 eBay 美国站、轻小不带电的商品”生成无货源市场报告，Listing 继续阻断。
7. “这是我的供应商链接”建立商品事实包并只询问缺失事实。
8. 已有货源商家可以跳过选品，直接进入事实采集与 Listing。
9. 来源缺少库存、发货地或图片权利时，AI 不编造且不能公开发布。
10. 商品事实齐全时，Listing 标题、描述、类目、属性和账号政策由捷境预填。
11. Inventory API 未发布 Offer 不显示“去 Seller Hub 编辑”入口。
12. “转到 eBay 自己补充”只通过 Seller Hub Draft 接力适配器创建 Draft，不调用公开发布。
13. 同一 SKU 不能同时由 Inventory API Offer 和 Seller Hub Draft 两种模式写入。
14. Seller Hub 接力后捷境停止覆盖，发布结果只有只读对账命中后才能记录成功。
15. 前端与后端不再展示矛盾意图或任务卡。
16. 任何真实发布、改价、库存或付款请求都停在确认中心。

## 11. 成功标准

- 开放域测试集中普通问题正确路由率达到 95% 以上；
- 必须获取最新数据的问题不再使用无来源旧知识冒充实时答案；
- 连续追问能够保持当前实体和目标；
- 普通咨询错误生成经营任务的比例接近零；
- 无货源市场报告不会生成可发布 Listing；
- 已有货源商家无需手填 eBay 页面即可生成完整捷境 Listing 草稿；
- 商家既可以在捷境逐项修改，也可以明确选择单向转交 Seller Hub Draft；两种模式不会造成同一 SKU 双写；
- 商品事实、AI 建议和未知项在数据与界面上可区分；
- 真实发布、支付和 Secret 边界保持不变；
- 模型升级有成本、时延和使用原因记录，普通问题不无条件使用 Pro。

## 12. 被否决方案

- 继续堆叠关键词路由：无法覆盖开放域复杂问题，且会重复产生否定句和上下文误判。
- 所有请求固定使用最强模型：成本更高，也不能解决工具、状态和错误路由问题。
- 建设捷境货源池或代商家对接供应商：偏离当前 SaaS 边界，并引入库存、履约、采购、图片权利和供应关系责任。
- 让商家自己去 eBay 填 Listing：没有实现捷境从商品事实到刊登的核心价值。
- 把 Inventory API Offer 当成 Seller Hub Draft，或宣称可在两个系统实时双向编辑：与 eBay 官方编辑边界不符，会造成覆盖和审计冲突。
