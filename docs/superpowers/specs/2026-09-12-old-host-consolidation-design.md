# 旧主机合并到生产主机：迁移方案

日期：2026-09-12。

状态：用户在获知迁移保全、切换验证、旧机退役建议后明确要求“按刚才建议、三个阶段继续推进”，本方案进入实施准备，不再重复询问迁移意愿。尚未执行数据复制、停写、切换域名、停机或修改自动续费。Cloudflare 登录待恢复；真正切换、停写与自动续费设置按各阶段的已核验对象和动作边界落实，不由准备成功推定已完成。

## 1. 目标与完成定义

将旧 40 GB 主机上所有需保留的捷境数据、配置、历史证据与必要运行职责移出旧机，使其不再成为网站、运营后台、监控、恢复或部署的必要依赖；完成可回滚验证后退役旧机，降低长期费用。

“全部迁移”指数据和必要职责不遗漏，不指旧系统覆盖新系统，也不要求旧程序全部重复运行。原商家主站、托管 PostgreSQL、生产 Vault、用户记录及业务权限保持不变。

本次不进行真实收费、退款、eBay 操作、商品生成或 UI 改造。不购买新服务器或付费 KMS。取消自动续费、释放实例、删除旧数据不包含在准备阶段；须在迁移验收完成后单独落实。

完成必须同时满足：

1. 持久数据清单已全覆盖，归档在新机和独立于新机的恢复位置各有一份，均已验证可解密、内容校验及恢复。
2. `ops.jiejing.shop` 与任何依赖旧机的域名入口已在新机提供相同受控能力。
3. 旧 Worker、Vault、隧道、runner、cron 等职责有明确的保留、替代或退役结论，无未知依赖。
4. 主站、ops 隔离、权限、退款能力配置及必要定时任务经过无资金动作验证。
5. 旧机可回滚停止后，新机独立覆盖至少一个已确认的关键维护周期（当前已知为 12 小时，另计调度抖动与执行预算），使用停机后新产生的证据证明无旧机依赖；恢复旧机路径明确，不需要回退共享业务数据库。

任何一项未满足，只能报告“迁移准备中/部分完成”，不能报告“旧机可安全释放”。

## 3. 方案比较与推荐

### A：完整数据保全 + 必要入口/职责合并（推荐）

保全旧机持久数据和恢复材料，新机增加隔离的 ops 前端/路由，核验兼容后复用现有生产内部 API。旧 Worker、runner 不重复启动。优点是只保留一套业务后端和必要入口，长期成本、版本漂移与资源消耗最低。

复用生产 API 不是已验证结论；内部管理员资格、会话、数据库身份、退款能力和存储引用未通过时，不切流量。

### B：完整数据保全 + 独立旧 ops/API 过渡栈

仅在 A 的兼容性核验不通过且无法作最小兼容修复时评估。使用独立项目、网络、卷和私有目录，不复制旧 Worker/runner 的自动运行状态。该方案维护两套 API 与可能的 Vault，资源和版本负担较高；不得静默从 A 切到 B，应把具体差异重新交用户确认。

### C：整盘克隆后覆盖生产（不采用）

会覆盖生产文件、卷或服务身份，破坏已部署版本。新旧 Compose 项目都叫 `deploy`，且有同名服务与卷，不能直接把旧 compose 或 ops_switch 脚本换主机运行。

## 4. 数据保全设计

### 清单与范围

先生成只含路径/种类/大小/挂载关系的受保护完整清单。之前深度和条数受限的扫描不能替代完整清单。

必须覆盖：

- `/opt/jiejing-staging` 的当前文件、所有 release、备份、归档与私有配置引用。
- 全部 Docker 持久卷，包括当前 staging 数据卷、所有旧 Vault 卷及未分类卷；无引用不构成删除依据。
- `/home/ubuntu`、root 和其他用户的捷境相关持久文件；runner 工作区和运行配置只归档、不恢复执行。
- Caddy、systemd、cron、Cloudflared、SSH/防火墙相关恢复配置；不把这些系统配置覆盖到新机。
- 挂载或服务引用指向上述范围外的持久文件，以及恢复旧运行版本所需的固定镜像或可验证重建材料。

不复制 `/proc`、`/sys`、`/dev`、运行中 socket 等内核瞬态数据。操作系统包和可重建缓存可保存版本清单而非自动恢复，但必须在清单中明确分类；未归类的用户数据一律保留，不能静默跳过。

### 一致性与秘密边界

先确认恢复旧 Vault 的现有材料可用，再安排旧后台维护；不能停止后才发现无法解封。当前 file 后端需离线一致性备份；不能套用仅适用于 Raft 的 snapshot 命令。

区分预归档与最终封存：先保全静态数据和恢复基线，候选配置、门禁与无外部写入的兼容性验证尽量前置，不能让旧后台停写等待整轮开发和观察。首次一致性备份若需短停，恢复服务后产生的新写入必须登记为待补增量，不能把第一次归档当作最终备份。

切换前短暂停止旧侧必要写入者，等待任务安全退出，以明确源截止时间和服务状态补齐最终增量，对数据卷和 Vault 取得一致归档。归档保留属主、权限、ACL、扩展属性、链接和稀疏文件语义；最终清单/hash 绑定截止点。没有可靠增量机制的卷在此窗口做完整一致性归档。未测得复制时长前，不承诺具体停写分钟数。

2026-09-15 一致性判定澄清（不减少既定保全范围）：C组的`/var/log`、`/var/cache`、`/var/tmp`、`/tmp`中，业务数据及任何未分类条目仍适用完整保留、必要writer停写和稳定最终归档的原门禁。仅逐项已有业务归属证据、确认属于OS运行日志的条目，可采用“完整历史留存＋明确截止的活动日志原生导出或快照”，独立记录捕获区间、对象及验证证据；这不是全OS静止或位复制证明。管理SSH引起的截止后日志允许继续留在旧机，不停止sshd/journald、不删除源、不忽略tar警告或放宽原归档源稳定检查。不能因cache/tmp目录名排除数据，也不能据此预先将任何C条目标为已分类、已保全或final。具体capture实现及验收仍须方案、测试和主审；无新增付费服务，旧失败不洗绿，日志留存通过不直接授权退役。

最终封存后旧侧业务及必要封存数据的写入者保持停止，旧业务路由转至新入口或明确维护态，不能继续接受这类独立本地写入；不包括上述已逐项核实并明确捕获截止的系统运维日志写入。若失败恢复旧业务或必要封存数据写入者，原封存验收立即失效，须重新补增量与校验；旧机与备份均不删除。

秘密仅在后端受控搬运，使用经过审查的成熟加密工具；密钥/Token/DSN 不进入聊天、stdout、日志、Git、文档或前端。不得自行实现加密格式。模型只接收校验通过/失败、数量、归档大小及不含秘密内容的回执。

新机归档放独立 root 私有路径，不落入主站可访问目录，不自动执行。恢复材料与加密归档不能只放在同一新机；本地 D 盘本轮有约 239 GiB 空闲，可作为独立加密恢复副本的候选位置，实施前核对磁盘身份与专用目录权限。不要占用当前仅约 15 GiB 空闲的 C 盘承接大归档。

### 空间与恢复验收

不预设压缩率。按清单计算逻辑/分配大小、固定镜像、归档、必要解包及迁移峰值预算，新机全程至少保留 10 GiB 可用空间；达不到则停止并调整分段归档/独立恢复副本方案，不先买扩容。

传输可分段续接，回执绑定源清单和每段 hash；不得因连接中断重新覆盖已经校验的段。恢复验证在隔离且无外部网络的环境进行，不启动能消费队列、退款、发邮件或调用平台的旧服务。校验文件清单、内容与元信息；验证旧 Vault 可解封只回报结果，不读取商家密钥内容。共享托管 PostgreSQL 不因旧机退役而迁回本地或用旧快照覆盖。

## 5. 运行入口与职责

### ops 与域名

保留 `app.jiejing.shop` 现有主站规则及 active release。新机既有 Caddy 增加独立 ops 站点，接专用 ops Nginx，后者仅暴露既有资产与精确路径/方法白名单，并向生产内部 API 保留准确 Host。不能把 ops 简单转到公开 app 域，因为商家域有意拒绝内部接口。

新组件使用独立名称、网络和受控目录，任何共享网络连接必须显式声明；不复用旧 `deploy` 项目身份、不另起争用 80/443 的代理、不覆盖生产卷。日后正式发布工具也须持续包含/保留该 ops 配置，避免下一次主站部署把迁移结果覆盖掉。

核对 `jiejing.shop` 根域重定向、`ops.jiejing.shop`、旧 app 入口、pilot 与 Cloudflared 的实际映射。源码显示旧 Caddy 负责根域 308 跳转，新 Caddy 尚无根域配置；实际 DNS/Cloudflare 规则仍以控制台为准。本机 198.18.* DNS 是代理合成结果，不当作源站证据。

先验证候选私有入口、TLS 准备及后台权限，再切精确域名记录；保留原记录和回滚证据。2026-09-23用户已具体认可后台经过Cloudflare的推荐：ops迁NEW并由DNS-only改proxied/Auto，兼容NEW已存在的Cloudflare-only源站保护；根域仍proxied/Auto，app/pilot不动。公网TLS、资源和匿名隔离验收已完成，详见当前执行索引及任务`dns-ops-cutover-20260923.json`。不扩大源站直接访问范围，不改变微信支付和退款的既有app回调地址；原“保持ops DNS-only”不再作为续接指令。

### API、数据库与 Worker

现有 API 已含精确 ops Host 与内部名单+owner/admin验证，但必须重新核对当前生产运行资格。后端如需使用已有凭据进行只读数据库身份核验，凭据留在容器内；使用显式只读事务、短超时，仅返回身份比较结果，不读取业务内容、不初始化仓库或执行迁移。

不要运行 `jiejing_worker_cli.py status` 作为只读检查：其初始化路径会建立目录并调用 repository.initialize。不要通过重跑同步、OAuth、真实支付/退款来证明迁移。

确认旧 Worker 对应数据库/队列/任务职责及未完成任务后再停用；不能只凭端点相似或 `SKIP LOCKED` 假设任务不重复。新机不自动启动旧 Worker。若存在独立本地业务库，先制定对应增量与回滚协议；不得直接合并未知库。

### Vault、构建与调度

旧 Vault 数据完整保留，但不并入/覆盖生产 Vault。若现有生产引用不能覆盖旧 ops 所需引用，则停止 A 的切换，明确兼容方案；不要让商家重复输入模型密钥或重新 OAuth。

普通 CI/Cloud Fallback 已使用 GitHub 托管环境，现有本地生产部署路径无需旧 runner。旧 runner不搬进生产；归档其配置后，确认没有运行或排队任务，再退役对应专用工作流。

仓库六份流程仍依赖旧 staging runner，只有 CLS 每 12 小时流程自动调度。新机已有 root systemd 证据刷新 timer，但必须核对职责覆盖后才移除旧定时流程。不能把 `runs-on` 直接改为 GitHub 托管机，因为旧脚本依赖本机 Docker、私有目录及发布身份。

COS synthetic probe 只证明存储通道，不是商家数据库/Vault备份。必须分开验证真实备份、恢复与监控职责。旧 cron 内容及宿主自定义单元尚未完整分类，不因 timer 列表没有捷境条目而认定无依赖。

## 6. 执行阶段及失败处理

1. **准备**：具体方案确认、完整依赖清单、只读兼容核验、Cloudflare 登录、恢复材料与空间预算；失败不动服务。
2. **预保全与候选准备**：静态数据预归档、必要的首次一致性备份与隔离恢复验证；本地专项测试、精确同源门禁与 CI、官方发布路径扩展的 dry-run、隔离候选测试。不套用旧 237 门禁证明新改动；首次备份后恢复写入须记录待补增量，不能将开发时间算入持续维护窗口。
3. **最终封存**：候选准备通过后，取得旧后台停写许可，停止旧侧必要写入者并等待安全退出，补齐增量或完整归档，绑定最终源截止点，验证新机与独立恢复副本。失败恢复旧服务并使封存失效，不进入切换。
4. **切换**：落实本批发布/切换确认，验证基线未漂移后一次执行；旧侧本地写入者不重新启动。任何失败只回退本次 ops 配置/路由，不回退业务数据库或生产 Vault；若恢复旧写入，重新补全封存。
5. **独立运行观察**：主站与ops UI、匿名/非管理员隔离、只读反馈/退款列表及能力投影通过后，获确认可回滚停止旧机。在旧机离线的条件下覆盖至少一个已确认关键任务完整周期及其抖动/执行预算，以停机后证据验证；不创建真实收费、退款或eBay操作。
6. **退役**：独立运行观察通过、最终归档仍与停止源一致后，再核对并处理自动续费，数据保留/释放另行确认。不得用复制完成、停机前维护证据或短时健康成功替代此阶段。

若回滚期间候选产生独立本地写入，必须按预先验证的增量回迁协议处理；未制定该协议就禁止候选产生这些写入。共享数据库的回滚仅涉及路由和代码，不使用旧快照覆盖新交易。

## 7. 验证清单

- 归档全覆盖、无秘密输出、完整 hash、可解密及隔离恢复；旧文件不执行。
- 新旧卷/项目/网络/端口无冲突，原三用户 dirty 不混入发布，生产原基线可回滚。
- 原平板聊天/报告/R8/素材记录只读仍可见，不另建演练或重生成。
- 主站 health/deep正常，readiness各状态分别回报；付款能力不冒充退款执行或eBay发布证明。
- ops六资产同版、精确域名/方法/权限、商家域内部路径404；匿名与非内部管理员拒绝。
- 退款本地替身合同通过，线上仅比对能力及读列表；不执行/query真实退款。
- 域名重定向、TLS、回调地址不漂移，旧隧道用途有明确结论。
- Worker职责无遗漏、不重复启动；GitHub排队/调度无旧机遗留依赖；真实备份与synthetic探针分开验收。
- 最终归档绑定最后写入截止点，回滚恢复旧写入后必须重新补全封存。
