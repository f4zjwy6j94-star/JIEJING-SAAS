# 捷境成熟商家界面与运营隔离设计

日期：2026-08-27  
状态：方案 B 已由用户确认；本书面规格待用户复核  
设计标识：`merchant_surface_ops_isolation_v1`

## 1. 决策摘要

捷境继续采用 eBay-first AI CEO SaaS 定位。本轮不推倒重写后端，不删除历史数据，也不改变现有高风险确认边界；重点是把已经具备的能力整理成一个成熟、可信、低学习成本的商家产品。

本轮固定执行以下决策：

1. `app.jiejing.shop` 永远只显示商家产品界面。即使内部主理人账号登录，也不能在商家端看到上线准备度、部署证据、支付验收、假支付方、内部测试额度或运行诊断。
2. 内部上线、支付验收、可靠性、成本、审计和发布门禁统一归入 `ops.jiejing.shop`。
3. Settings 顶层只保留五个商家入口：账号与店铺、AI 与素材、店铺数据、团队权限、套餐与付款。总览可以作为落地页，但不能作为第六个并列设置标签。
4. 每个商品项目只显示一个当前阶段、一个主要阻断和一个下一步动作；不再由各页面分别计算互相矛盾的完成百分比。
5. AI CEO、Listing、素材、确认中心、客服和工作记录共享同一当前项目上下文。历史验收数据保留，但默认归档，不得污染当前项目。
6. 官网继续保持一个填充式主按钮“免费生成第一条草稿”，内容收敛为商家价值、三步流程、可信边界、套餐和常见问题。
7. 当前香炉演练继续复用现有 SKU 和未发布 Offer；账号限制解除前不得盲目重试发布，也不得创建重复 Offer。
8. 真实外观的演示店铺、商品、客服指标和预置会话只能存在于测试 fixture；生产商家 bundle 不得携带这些种子数据作为回退内容。

## 2. 当前问题与产品风险

### 2.1 商家端与运营端混合

当前 `app.js` 会根据内部角色在商家 Settings 中追加“主理人高级”标签，并渲染正式上线准备度、生产状态、运行队列、验收证据和发布记录。套餐页还可能展示内部测试额度、1 元支付验收、隔离假支付方和 Owner 操作提示。

这不是措辞问题，而是界面边界错误：同一个人使用内部账号登录商家产品时，也应该体验普通商家的真实产品，而不是看运营控制台。

### 2.2 当前项目状态不一致

Listing、素材、确认中心、客服和记录页从不同对象计算状态，已出现以下可见矛盾：

- 同一商品出现不同完成百分比和不同缺失项数量；
- 素材同时被描述为“可以回写”和“概念图不可回写”；
- 已保存的 eBay 未发布 Offer 与 AI CEO 回答中的旧缺口不一致；
- 确认中心与其他页面使用不同待办集合，导致数量和对象不一致；
- 历史手机壳、历史 QA 对话和当前香炉项目混在同一默认视图。

### 2.3 商家语言仍混入工程语言

客户页面仍可能出现 `production_ready`、`AssetManifest`、provider、内部布尔字段、原始 Offer/SKU 调试信息、验收任务和失败堆栈。技术证据需要保留，但不能成为商家默认阅读负担。

### 2.4 官网和工作台信息密度过高

首页首屏存在多个竞争入口、说明重复和过重的流程图。工作台多个页面重复解释安全边界，却没有始终把“当前要做什么”放在最前面。成熟 SaaS 应优先显示当前结果、阻断和下一步，详细原理按需展开。

### 2.5 生产 bundle 仍携带演示种子

静态前端仍内置真实外观的演示店铺、商品草稿、客服 KPI 和预置对话。即使正常登录路径会用真实数据覆盖，这些种子仍可能在未登录、接口失败或异常回退时泄漏，造成假数据被误认为商家事实。运行时隐藏不是合格修复，生产 bundle 必须移除，自动化测试改用独立 fixture 注入。

## 3. 产品边界与非目标

### 3.1 本轮范围

- 商家端与运营端的前端物理隔离；
- 更新仓库级产品守则，把“内部 owner surface”明确限定为 `ops.jiejing.shop`，不再允许解释为商家 Settings；
- Settings、套餐、素材额度和团队权限的商家化；
- 当前商品项目的统一展示状态；
- AI CEO 当前项目上下文与结果展示收敛；
- Listing、素材、确认、客服和记录的项目一致性；
- 生产 bundle 演示种子清除与测试 fixture 隔离；
- 官网结构、文案、视觉层级和移动端可用性；
- 对应静态合同、行为合同、浏览器回归和生产验证。

### 3.2 非目标

- 不改变已确认的免费体验、99 元和 199 元套餐权益；
- 不重构微信支付、素材点账本或 eBay OAuth；
- 不删除历史会话、项目、素材、确认单或执行记录；
- 不把捷境改成货源平台，不承诺替商家核验或提供供应商；
- 不开放任意或批量真实平台写入开关；现有确认门控的未发布草稿保存和“精确 Offer 单次 publish”窄适配器继续保留，但后者仍要求账号恢复、预检通过和动作时确认；
- 不在本轮进行整套前端框架迁移；
- 不因 UI 整改触发真实收费、退款、广告、采购或 eBay 公开发布。

## 4. 商家端与运营端隔离

### 4.1 域名与角色矩阵

| 入口 | 普通商家 | 内部主理人/运营角色 |
| --- | --- | --- |
| `app.jiejing.shop` | 商家工作台 | 仍然只显示商家工作台 |
| `ops.jiejing.shop` | 401/403，不返回运营数据 | 按内部角色显示运营后台 |
| `app.jiejing.shop/ops.html` | 404 | 仍为 404 |

角色只决定是否有权进入运营后台，不能决定商家端是否插入内部标签。

### 4.2 前端物理边界

- `app.html`、`app.js` 和商家样式不得包含主理人上线面板、支付验收面板和部署证据模板。
- 商家端不得请求 owner launch、内部 payment rehearsal、生产证据或发布门禁接口。
- 现有内部渲染逻辑迁入 `ops.html`、`ops.js` 和 `ops.css`，优先放入“系统可靠性”或新增的“上线与运行”视图。
- 商家与运营产物必须是两个独立 bundle；商家 bundle 不得懒加载、动态导入或以字符串模板保留运营模块。
- `/owner/*` API 继续使用现有内部角色授权；同时增加入口边界：来自 `app.jiejing.shop` 的浏览器请求即使携带内部管理员会话也要拒绝，只有 `ops.jiejing.shop` 可以进入精确 allowlist。不能把整个后端泛开放给 ops。
- 商家 API 永远返回 merchant-safe projection，不能因为调用者是内部管理员就返回未净化套餐、素材点或上线字段；完整内部对象只从 `/owner/*` 提供给 ops。
- 即使在 ops，后端也永不返回、页面也永不显示环境变量原值、Token、refresh token、client secret、支付密钥、模型密钥或 Vault 凭据；只允许布尔状态、后端引用、时间和脱敏证据。
- 部署代理为 app 主机增加优先级高于通用 API 代理的内部路径拒绝规则；ops 主机只明确开放需要的 launch、readiness、release、reliability 和 payment-rehearsal 路由。
- 普通商家访问内部 API 保持 403。运营入口即使无数据也显示真实空状态，不插入演示数字。
- 不通过 CSS 隐藏、角色条件拼接或运行时替换制造“看不见”。商家 bundle 本身不应包含这些可渲染内容。

### 4.3 商家 Settings

Settings 顶层固定为五类：

1. **账号与店铺**：捷境账号、eBay 连接、账号健康、发布能力状态和唯一下一步；不展示 OAuth secret、token 或内部错误响应。
2. **AI 与素材**：把文字分析、图片识别、联网搜索、图片生成拆成四项独立能力，分别显示是否可用和用量。明确说明不支持看图的文本模型不会被要求猜图，图片先由支持视觉的服务提取事实。商家默认只看总可用素材点；内部验收 bucket 不进入 merchant projection，只有后端 entitlement 明确标记为真实商家赠送时才显示“活动赠送额度”。
3. **店铺数据**：官方数据更新时间、覆盖范围、来源和缺口；同步动作明确只读，不重复授权。
4. **团队权限**：默认显示当前角色和关键确认边界；完整权限矩阵折叠展开，使用“负责人”等商家角色名，不显示原始权限字符串。
5. **套餐与付款**：当前套餐、权益、订单、付款和退款状态；套餐名称全站统一为“免费体验、有店铺、多店铺”，并明确套餐已包含相应素材点、用完后才需要加购；不显示验收脚本、假支付方、测试订单操作或内部 readiness。

Settings 落地页只回答“当前状态”和“去哪里处理”，不重复每个子页的长说明。

## 5. 当前商品项目统一状态

### 5.1 阶段模型

所有业务页面共享以下八个阶段：

1. `source`：商品来源与图片使用权；
2. `research`：市场调研与候选选择；
3. `facts`：SKU、材质、尺寸、重量、成本、售价、库存、发货地等商品事实；
4. `media`：素材生成、事实一致性和图片权利复核；
5. `listing`：类目、属性、标题、描述、政策和利润检查；
6. `draft`：eBay Inventory Item 与未发布 Offer；
7. `publish`：账号健康、发布预检、精确确认和幂等公开发布；
8. `record`：Item ID、Offer ID、执行记录、审计证据和结果页。

每阶段只能使用以下展示状态：`未开始`、`进行中`、`待补资料`、`待商家核对`、`可以继续`、`已完成`、`已阻断`、`执行失败`。

### 5.2 唯一展示模型

后端根据权威工件生成一个 merchant-safe、带版本的 `merchantProjectStatus` 快照；本轮不新增数据库表。一次刷新只生成一个证据截止点，AI CEO、Listing、素材、确认、客服和记录页只消费同一快照，不能各自重新推导总体状态。前端只负责格式化和局部展示。快照至少返回：

- `project_id`、`listing_id`、`sku`；
- `current_stage`、`stage_statuses`；
- `primary_blocker`；
- `next_action`；
- `source_summary`、`media_summary`、`listing_summary`、`ebay_summary`；
- `snapshot_version`、`evidence_cutoff`；
- `latest_evidence_at`；
- `historical=false`。

数据优先级固定为：最新 eBay 执行/只读恢复证据 > 当前 Listing 权威状态 > 当前素材审核 > 当前 AI CEO 结构化报告 > 纯文本会话。历史执行只能作为时间线，不得覆盖当前状态。

当前页面和项目必须进入 URL，例如 `?view=listing&project=<opaque_id>`。刷新、返回和复制链接后仍打开同一授权项目；项目引用使用不透明 ID，不在 URL 放 Secret 或敏感资料。

### 5.3 进度展示

- 默认展示“当前阶段 + 已完成阶段数”，例如“eBay 草稿 · 已完成 6/8”；不展示来源不一致的百分比。
- 缺失字段只由同一聚合器生成一次，各页面复用同一个计数和清单。
- 同一项目最多突出一个主要阻断。其他缺口放在展开区。
- 每页只突出一个主行动按钮；已经完成的动作显示结果，不继续显示可重复执行按钮。

### 5.4 当前香炉项目的真实状态

- 必须锁定并复用 SKU `JJ-INCENSE-JC2023041300002-01`、Offer `245675556011` 和该草稿权威记录绑定的当前 `listing_project_identity`；任一不匹配就阻断，不得创建第二个同商品 Offer。
- Offer 当前为未发布状态；保存草稿成功不等于公开发布成功。
- eBay 官方账号限制解除前，`publish` 阶段保持“已阻断/等待平台审核”，下一步只能是定向只读复核。
- 平台确认账号恢复后，先做精确预检；最终公开发布前再次展示标题、类目、价格、库存、SKU 和 Offer，并请求动作时确认。
- 超时或结果不确定时先按 SKU/Offer 查询远端状态，禁止盲目重试。

## 6. 页面设计

### 6.1 日常导航

日常导航收敛为：

- AI CEO
- 商品项目
- 素材工坊
- 客服与物流
- 确认中心
- 工作记录
- 设置与账户

“批量铺货”在单商品闭环稳定前降为商品项目中的次级入口，不继续宣传捷境会替商家寻找或核验货源。

### 6.2 AI CEO

- 默认打开当前项目会话；通用问答与项目对话明确区分。
- 回答采用“结论、依据、资料缺口、下一步”结构。
- 当前 Listing 的 SKU、商品事实、已审核素材、Offer 和发布状态进入结构化上下文。
- 不向商家显示内部布尔字段、路由原因、原始失败堆栈或模型供应商调试信息。
- 历史 QA、旧失败和旧商品对话移入“历史会话”，默认折叠；保留审计，不删除。
- 表格必须以真实表格或卡片渲染，不显示 Markdown 管道文本。

### 6.3 商品项目与 Listing

- 顶部统一显示商品名、SKU、当前阶段、主要阻断和主行动。
- 商品资料模块是商家补充必填事实的唯一入口；AI CEO 可以引导，但不要求商家在对话中反复回答已经填写的字段。
- 商家可以在捷境内修改 AI 已填字段；普通 Listing 工作不引导商家打开 eBay 手工填写。
- Offer、执行 ID 等技术引用放入“技术详情”，默认折叠。

### 6.4 素材工坊

- 默认只显示当前任务、当前可用素材和一个主行动。
- “素材清单（AssetManifest）”在商家端统一写作“商品素材”；内部技术名仅在 ops 审计中保留。
- 已回写的素材显示“已加入 Listing 草稿”，按钮禁用或变成“查看 Listing”。
- 概念图明确显示“仅供构图参考，不可用于 Listing”；它不能同时计入可用素材。
- 历史版本折叠为时间线，不与当前版本并列抢占首屏。
- 商家端不显示素材供应商、provider 状态或美元成本；真实成本只进入 ops，商家只看到本次使用的素材点和结果状态。

### 6.5 确认中心、客服与记录

- 确认中心只使用一套待办集合和同一个项目过滤条件，标题计数、列表数量和导航角标必须一致。
- 客服页只统计客服相关确认，不把 eBay 同步或发布确认计入客服待办。
- 工作记录默认过滤“当前项目”；历史验收、旧手机壳和系统 QA 进入“历史验收”筛选。
- 每条记录先显示商家可读结果；技术明细展开后才显示脱敏 ID、错误码和时间线。

## 7. 官网收敛

官网保持六个核心板块：

1. 首屏价值主张；
2. 商家最终得到的草稿结构；
3. 三步工作流；
4. 资料来源、风险初筛与确认边界；
5. 免费体验、有店铺、多店铺三类入口和套餐；
6. 常见问题与支持。

具体约束：

- 唯一填充式主按钮固定为“免费生成第一条草稿”；登录使用普通文字链接。
- `index.html` 是唯一公开营销首页；`app.html` 未登录时只呈现简洁登录/注册入口和必要边界，不再复制一整套营销首页。
- 首屏不放复杂角色放射图、开发进度、模型 API、内部架构或 readiness。
- 标题在常见桌面宽度不超过三行，在手机宽度不使用超大字号挤满首屏。
- 套餐按“免费体验、有店铺、多店铺”排列，数值只读取现有权威套餐合同。
- 不使用固定商品案例、虚假客户、虚假销量或无法证明的成功率。
- “侵权风险初筛，仍需商家核对”是统一边界，不出现“侵权检测通过”。
- 已退休的营销区、固定商品故事和旧产品模式必须从生产 DOM 与 bundle 物理删除，不能只靠 `hidden` 或运行时脚本遮挡。

## 8. 视觉、可访问性与性能

- 使用白色/近白背景、克制青绿色、少量琥珀警示和不超过 8px 圆角。
- 首屏、页面标题和项目卡片建立稳定字号层级；同一屏不重复多个同等级标题。
- 可点击目标在移动端不小于 44×44 CSS 像素。
- 所有输入都有可见标签、稳定 `name` 和合理 `autocomplete`；不能只依赖 placeholder。
- 键盘焦点必须可见；禁止无替代的 `outline: none/0`。
- 页面导航优先使用可复制、可打开新标签的链接；筛选和标签状态应反映到 URL。
- 非装饰图片提供 `width`、`height`、替代文本和延迟加载，减少布局跳动。
- 本轮优先移除商家 bundle 中的大段 owner 模板，并提取当前项目展示聚合器；不要求立即迁移框架或拆完全部单体文件。

## 9. 错误与空状态

- 先说明发生了什么，再说明数据是否已保存，最后给唯一下一步。
- 事实不足时显示“待补资料”，不得由 AI 猜测。
- 外部平台受限时显示平台事实和最近核验时间，不把旧失败永久当成当前状态，也不自动宣称已恢复。
- 页面局部请求失败时保留已成功区域；不把整页渲染成空白或通用错误。
- 新商家显示空白工作台；已有商家只显示自己有权限的数据。
- API 失败或会话失效时也只能显示安全空状态和错误提示，绝不回退到演示店铺、演示商品、预置会话或虚构 KPI。

## 10. 测试合同

实施采用纵向测试驱动，每个行为按一个红灯测试、最小实现、绿灯回归推进。

### 10.1 P0 商家/运营隔离

1. 内部主理人账号访问 `app.jiejing.shop` 时，Settings 仍只有五个商家标签。
2. 商家 DOM、JavaScript 可渲染模板和网络请求均不包含 owner launch、生产 readiness、支付验收和内部测试额度。
3. 普通商家访问全部 `/owner/*` API 返回 403；内部管理员从 app 域请求同样被入口边界拒绝。
4. `/billing/plans` 和素材点商家摘要对普通商家与内部管理员返回相同 merchant-safe 字段，不包含内部 bucket、验收或 launch 数据。
5. 内部主理人访问 `ops.jiejing.shop` 可以看到迁入的内部状态；无数据时显示真实空状态。
6. `app.jiejing.shop/ops.html` 保持 404。

现有测试中若仍强制商家模块包含 paid launch packet、内部限流、payment rehearsal 或 owner launch 标记，必须先把该断言改成红灯的隔离合同；不能为了保留旧测试而继续保留错误架构。

### 10.2 项目状态一致性

1. 同一项目在 AI CEO、Listing、素材、确认和记录页返回相同阶段、缺失项数量和主要阻断。
2. 已存在未发布 Offer 时不创建第二 Offer。
3. 概念素材不计入 Listing 可用素材；已回写素材不再显示可重复回写按钮。
4. 确认中心标题、角标和列表数量一致；客服只计算客服确认。
5. 当前项目默认不显示历史手机壳或历史 QA 数据，历史筛选仍可查看且数据未被删除。
6. 生产 `app.html`/`app.js` 不包含真实外观的演示店铺、商品、客服 KPI 或预置会话；测试通过 fixture 显式注入所需样本。
7. 刷新、浏览器返回和复制当前项目 URL 后，阶段、缺口和项目身份不漂移。

### 10.3 文案与界面

1. 商家端禁用词至少包含 `production_ready`、`can_accept_real_customers`、`provider_returned`、`AssetManifest`、`隔离假支付方`、`等待 Owner 发起`、`固定正式上线准备度`。
2. Settings 五类名称、首页单主 CTA 和侵权风险边界合同通过。
3. 桌面和移动端均无标题截断、重叠、横向滚动和不可点击控件。
4. 关键表单标签、键盘焦点、图片尺寸和导航 URL 状态检查通过。
5. 浏览器控制台没有相关错误或框架错误覆盖层。

### 10.4 安全与真实写入

- 测试和浏览器回归不触发 eBay OAuth、真实 publish、付款、退款、素材 provider 消费、广告或采购。
- eBay 受限状态下公开发布按钮保持阻断。
- 最终真实发布仍经过精确 Offer 确认和幂等执行。
- Secret 扫描、`node --check app.js`、相关专项测试和最新完整门禁全部通过。

## 11. 实施顺序

1. 增加商家端 owner 泄漏红灯测试，迁移内部面板到 ops。
2. 更新仓库级产品守则和旧测试，删除“商家 Settings 可以承载内部 owner 面板”的歧义。
3. 清理 Settings、套餐、素材额度和团队权限的内部文案与控件。
4. 建立当前项目展示聚合器，统一 Listing、素材、确认、客服和记录状态。
5. 收敛 AI CEO 当前项目上下文、历史归档和商家结果卡片。
6. 收敛官网结构、首屏、套餐排序和移动端样式。
7. 执行专项测试、Secret 扫描、JavaScript 语法检查和完整门禁。
8. 先做生产 dry-run，再按已批准的方案部署；核验 health、deep health、readiness 和 ops 隔离。
9. eBay 账号官方状态恢复后执行定向只读复核和发布预检；最终公开发布仍单独请求动作时确认。

## 12. 发布与回滚

- 本轮优先是前端模板、展示聚合和测试变化，不做破坏性数据库迁移。
- 部署使用现有不可变 release、manifest 和原子切换流程；失败时回滚到上一 release。
- 回滚不能删除新旧商家记录、素材、草稿、确认单或审计数据。
- 部署后必须分别报告：网站在线、私测可用、公开收费可用、真实平台写入可用。

## 13. 完成定义

只有同时满足以下条件，才能宣称“方案 B 已上线”：

- 商家端无任何内部上线、部署、支付验收或运行诊断内容；
- 主理人账号在商家端看到的仍是纯商家体验；
- ops 后台保留必要的内部证据并维持权限隔离；
- 当前香炉项目在所有页面显示一致且诚实的状态；
- 官网、桌面端和移动端通过视觉与交互回归；
- 专项测试与完整门禁通过；
- 正式生产部署和线上核验通过。

eBay 第一场演练是否公开发布成功是独立的外部结果：只有 eBay 限制解除、发布预检通过、获得精确动作时确认并只读核验到公开 Item ID 后，才可以写“已成功发布”。
