# 捷境产品质量核查与整改建议

日期：2026-10-04；2026-10-05 用户明确批准五项整改，进入实施。不是已完成、已部署或正式推广放行证明。

## 目标与边界

目标是现有 eBay-first AI CEO SaaS 能由商家独立、反复完成经营前置流程，错误可理解、任务可恢复、事实可追溯、收费与高风险执行边界可靠。本轮不推倒架构，不增加新平台、套餐、独立页面或付费基础设施，也不做视觉改版。

商家的自然语言意图和资料语义继续由大模型理解、整理。代码负责身份、范围、来源引用、金额/单位有效性、并发版本、幂等、计费和执行确认，不用关键词口令代替语义理解，也不让大模型自行放宽授权。

账号问题从本整改范围排除。真实发布、采购、付款、退款、广告和客户消息仍须在动作发生时确认。供应商事实、图片授权与经营参数不得编造。缺失实物测量、真实库存、合同或物流报价属于经营证据缺口；产品负责准确识别和引导，不保证凭软件消除。

## 当前已核实证据

- 仓库 HEAD 为 9412cfd；上一轮三商品的实际网页、35项保存/恢复/隔离及限定发布前回归记录仍有效，不因新核查被改写为“从未完成”。本轮未再次生成文案/图片、未重复门禁或部署。
- 发布前检查接口明确是只读：`jiejing_saas/api_server.py` 的 readonly_precheck 分支在凭据解析、任务/确认创建和平台适配器之前结束。
- `jiejing_saas/ebay_write_adapter.py::build_publish_readiness`：类目存在即可标 passed，库存位置 key 存在即可标 passed；asset_reachability 实际仅判断 URL 是否为 http/https。这个结果不等于 eBay 远端验证或图片实际可下载。
- 本轮纯本地最小复现：未核实类目/位置/图片地址均得到 passed；清空类目/位置变 blocked；无效图片 URL 变 blocked。网络调用0、生产写入0。对应546159；这证明结果主要反映本地字段状态，不证明真实发布可执行，也不说明执行授权已被绕过。
- 缺少包装长宽高时，后端产生3个不同字段错误，但 message 完全相同；前端逐条原样输出，导致三遍重复提示。复现中3条 issue、1种 message。业务校验仍有效，问题在反馈粒度和呈现。
- `app.js::renderSaasAiCeoMarketReportDeliveryMarkup` 使用市场调研交付卡；上一轮供应商事实更新出现“市场调研已保存”。本轮已定位渲染入口，尚未完成该消息类型的全链路重现，不把推断当已确认根因。
- 上一轮 AI 曾输出未获支持的轻量/耐用及不合适类目，由人工式审校纠正。三个原商品的数据完整性已实测，不等于模型质量在不同商品上均自动合格。

对重复提示和字段状态采用现有真实页面证据+纯本地函数复现；行为是固定映射，不添加生产日志。更深的事实更新卡归因仍要由原消息类型的端到端回归确定，不能仅改标题掩盖路由错误。

## 路线选择

1. **现有架构系统加固，推荐。** 聚焦资料→AI→文案→图片→检查这条主链路，保留项目、报告、素材和确认边界。以故障场景和证据标准验收，风险和范围可控。
2. **仅修提示文案。** 修改量小，但无法解决预检查含义、AI审校依赖以及异常恢复的质量目标，不足以支撑本次“产品级”要求。
3. **整体重构。** 当前没有证明需要推倒主架构；会扩大迁移和回归风险。仅在局部测试证明现有边界无法可靠隔离时，再提出有范围的重构设计。

## 推荐整改设计

### 1. 资料与证据

- 明确区分供应商参数、商家经营数据和系统建议；字段保留来源、单位、币种、所对应SKU及核实状态。
- 同SKU来源冲突不静默选值。提示具体冲突、受影响步骤与补证方式，允许先完成不依赖该字段的工作。
- 实物尺寸与包装尺寸、净重与运输重量、供应商发货地与卖家履约地点、MOQ与可售库存必须分开。
- 待核实字段继续保持未知，不能在恢复、切商品、重新生成或发布表预填时复活旧值。
- 对商家真正缺的资料提供集中、去重、可定位到字段的清单；已提供的资料不重复索取。

### 2. AI 结果质量

- 在现有模型链路加固主张与证据的一致性审查：材质、性能、认证、数量、尺寸、兼容性、产地等没有依据时不能作为确定的买家声明。
- 类目建议与已核验平台类目是不同状态；类目变化后按该类目核对属性要求，不沿用其他商品结果。
- 先审查既有通用事实约束和测试覆盖，再决定是否需要一次有界模型自纠；不无限重试，不为同一请求重复扣费。
- 商品事实更新、市场调研、费用咨询分别展示真实完成的任务；任何展示标签由实际任务结果决定，不以用户关键词分流。

### 3. 发布前检查的真实性与可操作性

- 明确“已填写/本地校验通过”“已由平台核实”“待核实/已过期”“阻断”的含义。
- 类目、库存位置、政策、图片可达性等没有新鲜且同账号/店铺/商品范围的证据时，不显示已经远端核实。
- 保持现有只读检查不解析平台凭据、不触发平台调用的边界。真实远端验证若有既有正式只读路径，复用其范围和证据；不存在时单列后续实现设计，不暗中在预检查里加外部调用。
- 规格错误按具体字段说明或合并去重，指出下一步；不要三遍相同句子，也不要只给“相关资料缺失”。
- 价格、运费、汇率及利润均保留口径；供应商人民币成本不自动等同刊登币种金额。

### 4. 连续性与异常恢复

- 复用既有项目/版本/云端检查点，测试刷新、回退、换商品、登录过期、网络失败和并发编辑。
- 无变更保存不创建无意义的新事实版本；真实变化仍触发相应依赖审查。
- 普通咨询不修改商品事实；重复点击、请求重放和超时恢复不重复建商品、生成图片或计费。
- 无论 UI 显示什么，服务端身份、租户、店铺、项目、来源版本和确认边界仍重新校验。

### 5. 新商家可用性与发布质量门槛

- 首先验证现有路径的准确性和可恢复性，再处理提示、按钮和状态一致性；本轮不更换视觉方向或导航。
- 完整流程应能由商家通过页面完成，不依赖开发者改数据库、手工调用业务API、补脚本或临时解释隐藏规则。
- 把真实商业条件和产品故障分开显示；不会因账号限制掩盖内部缺陷，也不会把合理的缺资料阻断当系统崩溃。

## 拟定验收标准

1. 已识别的阻断主流程或造成误导性放行的产品缺陷逐项有失败→修复→通过证据；已知故障不只改显示。
2. 三个原商品覆盖正常资料、资料矛盾、字段缺失、受限账号/模拟保护；至少两轮保存、刷新和跨商品恢复比较实际字段与资产。
3. 本地/隔离测试覆盖断网、超时、重复请求、登录过期、并发编辑和跨租户访问；无重复扣费/任务/刊登，无越权或串数据。
4. AI评测使用不同商品和相同意图的自然表达，检查事实一致性和任务类型；不能只靠固定口令或只检查HTTP成功。
5. 所有“已核验”状态必须有对应证据和范围；缺失、过期、矛盾均不能被标绿冒充远端通过。
6. 所有相关回归和新候选完整门禁通过后，才进入同源标准打包、部署审批/预演/发布及生产页面复验；旧版本273/273不能替代新改动验收。
7. 才能给出“适合小规模对外试用”的阶段结论。正式收费推广还需新商家独立使用反馈、受控真实发布及业务/收费/支持条件的独立证明，不给无证据的100%或永不出错保证。
