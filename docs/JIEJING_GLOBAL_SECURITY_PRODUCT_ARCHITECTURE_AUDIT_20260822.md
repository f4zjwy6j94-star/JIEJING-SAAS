# 捷境全局安全、产品与云架构审计（2026-08-22）

## 一、结论先行

捷境已经不是“只能演示的原型”：官网、注册登录、eBay 连接、AI 工作台、确认边界、微信支付、退款、eBay 未发布草稿、运营后台、Vault、托管 PostgreSQL、备份与恢复证明都已具备真实运行证据。

但它也还不能被描述为“近乎完美、可以放心大规模投放的成熟 SaaS”。当前最准确的判断是：

- **技术 MVP 成熟度：86/100**。核心路径已经跑通，权限、密钥边界、真实支付和低风险实写能力均有实证。
- **公开收费上线可信度：68/100**。能真实收费，但官网法律文本、公开 readiness、后台队列和运营数据之间存在明显事实不一致。
- **综合上线准备度：76/100**。适合小范围邀请制真实内测和首批付费客户；不适合马上大规模买流量或公开承诺高可用 SLA。

这不是项目“越做越差”。以前的分数主要衡量代码和流程是否完成；本次按真实收费 SaaS 标准加入了法律公开信息、运营数据可信度、依赖漏洞、云上单点和增长可发现性，所以标准更严格、暴露的问题更多。

本次没有发现正在被入侵、密钥外泄、越权读取客户数据或可直接绕过付款的证据。发现 0 个已证实 Critical、4 个 High、9 个 Medium/运营高优先级问题。

## 二、审计范围与边界

审计时间：2026-08-22（Asia/Shanghai）。

覆盖：

- `app.jiejing.shop` 官网、工作台、公开健康与 readiness、法律/支持页面、常见敏感路径、CORS、安全响应头。
- `ops.jiejing.shop` 运营数据中心、登录边界、经营指标、任务队列、告警、成本数据和会话失效行为。
- 腾讯云生产轻量服务器、旧运营服务器、CCN、托管 PostgreSQL、网络暴露、磁盘、容器、Vault、备份与恢复证据。
- 源码中的认证、Cookie、支付状态、任务生命周期、依赖锁定版本和生产配置。

边界：这是非破坏性只读审计。没有做真实退款、真实 eBay 发布、广告支出、破坏性渗透或密钥读取；运营后台部分模块在审计中途因现有会话过期而无法重新拉取，这一行为本身被记录为缺陷。

## 三、当前真实架构

```text
用户浏览器
   |
Cloudflare（DNS/CDN/WAF/TLS）
   |
生产轻量服务器 43.129.169.223（2核4G / 70GB / 30Mbps）
   |-- Caddy / 前端 / SaaS API / Worker
   |-- Vault / Token Renewer
   |
腾讯云 CCN（同地域内网互联）
   |
托管 PostgreSQL（香港，30GB）

运营人员
   |
ops.jiejing.shop
   |
旧运营服务器 43.129.205.244（运营台，直接公网源站）
```

这套方案对首批 MVP 客户是成本合理的：不用 Redis，不需要立刻再买一台数据库，也不需要现在就上复杂 Kubernetes。它的主要代价是应用、Worker 和 Vault 集中在一台生产轻量服务器上，服务器故障时会整体中断。

## 四、做得好的地方

1. **产品方向没有明显跑偏。** 官网围绕“eBay-first AI CEO SaaS”，讲清了商品、素材、客服、财务和自动推进，不是泛 ERP、聊天机器人或代理市场。
2. **高风险动作仍有人工确认。** eBay 公开发布、退款、广告/预算和广泛平台写入没有被悄悄放开。
3. **密钥边界正确。** 生产浏览器不保存 Bearer Token；Cookie 为 HttpOnly，生产启用 Secure；Vault 和后端端口未暴露公网。
4. **基础 Web 防护有效。** 官网有 HSTS、CSP、X-Frame-Options；跨域恶意请求未获得 CORS 放行；`.env`、`.git/config` 被阻断；登录失败信息未泄露账号是否存在。
5. **生产源站锁较好。** 非 Cloudflare 来源访问生产 80/443 被主机 nftables 拦截，内部 API/Vault 端口未对外开放。
6. **备份不是空口承诺。** PostgreSQL 最近 7 天自动物理备份成功，托管恢复演练和 Vault 纸质恢复证明均存在。
7. **真实业务能力已有证明。** eBay refresh 成功计数为 2；微信支付、退款、eBay 未发布草稿写入已启用；广泛真实平台写入仍关闭。

## 五、发现与优先级

### P1 / High：付费内测前必须处理

#### JJ-SEC-001 — 锁定依赖存在公开高危漏洞

- 严重度：High
- 证据：`requirements.saas.lock.txt:523` 锁定 `cryptography==46.0.7`；OSV 匹配多项 High 公告。`requirements.saas.lock.txt:700` 锁定 `protobuf==3.20.3`，匹配反序列化/递归深度相关 DoS 公告。
- 风险：密码学底层或不可信序列化输入可能扩大拒绝服务、内存安全或运行时风险。是否可直接利用取决于调用路径，但生产环境不应继续长期停留在已知受影响版本。
- 处理：将 `cryptography` 升至兼容的 `>=50.0.0`；将 `protobuf` 升至官方已修复且与腾讯 CLS SDK兼容的版本；重建镜像并跑完整生产门禁。把 OSV/pip-audit 加进 CI。

#### JJ-TRUTH-001 — 公开 readiness 与真实收费开关互相矛盾

- 严重度：High（产品事实/合规）
- 证据：公开 `/readiness/product-saas` 同时给出 `production_ready=true`、`can_accept_real_customers=true`，又在 billing provider 中给出 `public_charging_allowed=false`、`charge_now_allowed=false` 和“尚未批准切换”的 blocker。生产私有状态却确认公开收费、退款、未发布草稿保存均已开启。
- 根因：`jiejing_saas/api_server.py:8562-8613` 的 `_merchant_safe_billing_plan` 仍硬编码旧的关闭状态，尤其是 8576、8581、8584-8585、8612 附近。
- 风险：客户、运营人员、审计工具看到不同的“真相”；出故障时可能做出错误判断。
- 处理：建立单一、脱敏、可审计的发布状态源；公开 readiness 只移除秘密，不能伪造布尔值。支付开关、退款开关、eBay 写入边界与法律页共用同一版本化 release manifest。

#### JJ-LEGAL-001 — 法律、退款与支持页面仍是测试期文案

- 严重度：High（客户信任/支付争议）
- 证据：`refund-policy.html:32,36,52`、`support.html:32,51`、`privacy.html:31,45`、`terms.html:47,52` 仍写着“支付未全面开放”“人工确认”“以后补公开支持入口”等；实际已经可公开收费和退款。官网底部没有条款、隐私、退款和支持入口。
- 风险：发生支付争议或客户投诉时，公开承诺与真实产品不一致；用户找不到售后路径。
- 处理：先更新事实与联系路径，再邀请付费用户；首页页脚加入条款、隐私、风险披露、退款政策、支持入口及主体信息。法律最终文本应由合格专业人士复核。

### P1：真实运营数据必须修复

#### JJ-OPS-001 — 14 个任务长期卡在 queued，后台队列事实失真

- 严重度：High（运营数据完整性）
- 证据：生产数据库中 14 个商户任务自 8 月 13–15 日起仍为 `queued`，但没有 queue job/attempt；其中 9 个草稿保存、4 个库存地点设置、1 个发布确认。`api_server.py:3710-3723` 创建任务和确认，`api_server.py:7116-7413` 完成确认执行后只保存 execution result，没有同步关闭任务状态。
- 风险：运营后台看起来一直有积压；无法区分“等待确认、已完成、失败或真正在排队”，告警和决策都会被污染。
- 处理：增加 `waiting_confirmation -> executing -> completed/blocked/failed` 生命周期；确认执行必须原子更新任务和执行记录；上线一次性 reconciliation 修复历史 14 条。

#### JJ-OPS-002 — 运营会话过期后仍显示旧数据

- 严重度：Medium-High（运营信任）
- 证据：部分新请求已返回 `missing bearer token or session cookie`，但页面仍保留旧概览、成本、工作流和可靠性数据，并显示“真实数据已更新”。`ops.js:678-691` 的分模块捕获没有像完整刷新 `ops.js:670-674` 一样专门处理 401。
- 风险：运营人员可能把缓存当实时数据，尤其会误判收入、告警和任务积压。
- 处理：任何关键模块收到 401/403 时立即清空敏感缓存、显示“登录已过期”，返回登录页；每个卡片显示 `last_successful_refresh_at`，禁止失败后继续标“已更新”。

#### JJ-DATA-001 — 增长漏斗与成本口径不可直接用于决策

- 严重度：Medium
- 证据：30 天 `signup_started=0`、`signup_completed=10`；同时显示 73 独立访客、122 会话、8 商户账号、0 订阅、0 商业订单、0 收入。模型成本多行显示“不可用/覆盖不完整”。
- 风险：无法判断注册转化率、获客效果和毛利，容易在错误数据上做投放或定价决策。
- 处理：统一事件字典和匿名 visitor/session/account 映射；补 `signup_started` 埋点并重建漏斗；成本未覆盖时禁止展示虚假利润率。

### P2 / Medium：7 天内处理

#### JJ-OPS-003 — 运营源站直接暴露且缺少 HSTS

- 证据：`ops.jiejing.shop` 直接解析到 `43.129.205.244`，公网 80/443 可直达；响应无 HSTS；旧主机同时开放 22 和 2222；UFW 的 80/443 对所有 IPv4 开放。
- 风险：绕过 Cloudflare WAF/Bot/Access；增加登录面、扫描面和误配置风险。
- 处理：优先把运营台放到 Cloudflare Access/Tunnel 或至少 Cloudflare 代理并限制源站；添加 HSTS；SSH 收敛为一个受控入口并使用密钥/IP/VPN。

#### JJ-ARCH-001 — 单台生产服务器是明确单点

- 证据：前端、API、Worker、Vault 同机；数据库虽独立，但主机故障会造成整个产品不可用。
- 判断：对当前 0 订阅、邀请制 MVP 可以接受；对 SLA 或规模化付费不可接受。
- 处理：现在先写清恢复时间目标并完成整机恢复演练；达到 10–20 个稳定付费商户或承诺 SLA 前，再建设第二台热备/温备和健康切换，不建议现在盲目堆成本。

#### JJ-ARCH-002 — 腾讯云防火墙与主机防火墙策略不一致

- 证据：轻量服务器控制台仍把 80/443 设为所有 IPv4 可访问，真正的 Cloudflare-only 锁在主机 nftables。
- 风险：重装、迁移或 nftables 规则丢失时，源站会立即暴露。
- 处理：云防火墙也限制为 Cloudflare 地址段，或改用 Cloudflare Tunnel；把规则持久化和验证加入部署门禁。

#### JJ-DOMAIN-001 — `pilot.jiejing.shop` 仍公开且部署配置与仓库漂移

- 证据：`pilot.jiejing.shop` 仍返回与正式站相同页面；交接文件已把它定义为回滚通道。线上 Caddy 仍服务 pilot，而仓库生产 Caddy 只服务正式域，配置哈希不同。
- 风险：重复域名、客户混淆、搜索重复内容和下次部署覆盖当前行为。
- 处理：决定 pilot 仅内网/鉴权保留或 301 到正式域；把线上实际配置回归版本库并做配置漂移检测。

#### JJ-GROWTH-001 — 搜索引擎被完全禁止，sitemap 不是 XML

- 证据：`robots.txt` 对所有机器人 `Disallow: /`；`sitemap.xml` 返回首页 HTML；缺少 meta description、canonical、Open Graph/Twitter 元数据。
- 风险：自然搜索几乎无法建立；分享卡片和品牌可信度较弱。
- 处理：邀请制期间可保留 noindex；一旦决定公开获客，必须切换成明确的索引策略、真实 sitemap、canonical 和社交元数据。不要一边投放/宣传，一边又让官网完全不可发现。

#### JJ-WEB-001 — CSP 仍依赖 unsafe-inline，前后端单文件过大

- 证据：生产 CSP 的 `script-src`、`style-src` 允许 `'unsafe-inline'`；`app.js` 约 48,537 行/2.45 MB，`api_server.py` 约 10,730 行，`repository.py` 约 16,050 行，`index.html` 约 6,725 行。
- 风险：当前未发现可利用 XSS，可信模板 guard 和转义测试也通过；但任何未来插值遗漏的爆炸半径较大，代码审查和回归成本不断上升。
- 处理：逐步把内联脚本/样式外移并采用 nonce/hash CSP；按认证、计费、eBay、运营、任务协议拆分模块，不能做一次性大重写。

#### JJ-PERF-001 — AI 模型链路延迟偏高

- 证据：运营数据中模型提供方 P75 约 25.2 秒（5 个样本），成功率 100%。支付 P75 约 1.54 秒。
- 风险：虽然样本少，但 25 秒会被用户感知为“卡住”。
- 处理：前端显示阶段进度和可取消状态；区分首 token、完整响应、重试和模型调用；扩大样本后再决定模型切换或缓存，不要根据 5 次样本直接加机器。

#### JJ-BACKUP-001 — 数据库 7 天留存可用于 MVP，但容灾余量薄

- 证据：30GB 数据库仅使用约 243MB；最近 7 天物理备份成功；托管恢复演练距审计日约 12 天，配置最大新鲜度 30 天。
- 风险：长周期逻辑损坏、误删晚发现时，7 天窗口不足。
- 处理：9 月 9 日前再做一次恢复演练；增加每月长期保留备份/导出到独立 COS 或独立账户。无需现在扩容数据库。

#### JJ-CLOUD-001 — 运营主机磁盘使用率 84%

- 证据：40GB 磁盘已用约 32GB；`/opt/jiejing-staging` 约 11GB，actions runner 约 2.9GB，日志约 751MB；Docker 有约 8.9GB 镜像和 8.1GB build cache 可回收。
- 风险：继续部署和备份可能触发磁盘满，导致运营台/Runner 异常。
- 处理：先制定保留策略和备份验证，再做安全清理；设置 75/85/90% 分级告警。不要直接无差别 prune。

### P3 / Low：纳入维护清单

- `jiejing-postgres-staging-20260612` 实际承担生产数据库，名称仍含 staging；应重命名/打生产标签，避免误删。
- Vault token renewer 历史 restart count 为 28，目前健康且近一小时无新错误；对“重启次数增长”建立告警即可。
- 生产主机近期重启，`fwupd` 单元失败；不影响当前 SaaS，但应把 OS 补丁和重启窗口写进运维制度。

## 七、腾讯云成本与扩容判断

- 当前生产轻量服务器 2 核 4G、70GB、30Mbps，资源余量足：磁盘约 16%，内存约 2.4GiB 可用，不需要因为当前业务量升级。
- PostgreSQL 30GB 仅使用约 243MB，不需要扩容；Redis 当前也不是必须项。
- 生产轻量服务器到期时间为 **2026-09-22 11:21:49**，这是最近必须纳入日历的业务连续性事项。
- 当前 CCN 只连接同地域的普通 VPC 与轻量 VPC，没有跨地域带宽。按腾讯云现行公开规则，轻量 VPC 不计连接实例，免费额度延长至 2027-04-01；同地域普通 VPC 通信通常免费。政策到期后若仍按连接实例收费，普通香港 VPC 可能产生约 0.40 元/小时（约 288–298 元/月）的连接费，应在 2027 年 3 月重新评估，而不是现在迁移。

结论：**现在不买 Redis、不扩数据库、不升级 2 核 4G，也不为“看起来高级”增加 Kubernetes。** 先修事实一致性、法律支持、运营数据和依赖漏洞，这些比加机器更直接影响真实上线。

## 八、执行路线图

### 第一阶段：付费邀请前（最高优先级）

1. 修复 readiness 的收费状态硬编码，建立单一 release manifest。
2. 更新条款、隐私、退款、支持页和官网页脚；公开有效的售后入口。
3. 升级 `cryptography` / `protobuf`，重建镜像并跑完整安全、支付、退款、eBay 门禁。
4. 修复任务生命周期并对历史 14 条任务做一次性 reconciliation。
5. 修复运营台 401 后继续显示旧数据的问题。

完成这五项后，才把状态称为“可邀请真实付费客户”。

### 第二阶段：首批用户验证（7 天内）

1. 用 5–10 个目标 eBay 卖家做邀请制内测，不做大规模广告。
2. 修正漏斗埋点，定义“首次价值时刻”：例如完成 eBay 连接后生成并保存一条可用未发布草稿。
3. 修运营源站保护、HSTS、SSH 入口和磁盘保留策略。
4. 补真实 sitemap/meta；若仍封闭内测，则明确 noindex，不制造半公开状态。
5. 把 25 秒模型延迟拆成首响应与总耗时并持续监测。

### 第三阶段：出现稳定付费后

1. 达到 10–20 个稳定付费商户或准备承诺 SLA 时，再建设第二台应用节点/温备。
2. 增加独立长期备份、整机恢复演练、故障切换手册。
3. 依据实际模型成本、客服成本和客户留存调整 99/199/299 定价，不凭感觉扩基础设施。
4. 2027 年 3 月复核 CCN 新计费，比较“继续 CCN、迁移 CVM、数据库迁移或私网替代”的真实总成本。

## 九、对外口述介绍

### 一句话版本

> 捷境是一款面向 eBay 卖家的 AI CEO SaaS，它把商品上架、素材、客服和经营分析组织成可以持续推进的工作流，AI 负责做重复工作，发布、退款和预算等高风险动作仍由商家最后确认。

### 30 秒版本

> 很多 eBay 卖家不是不会做生意，而是每天被商品资料、上架、客服和数据整理这些重复工作拖住。捷境想做的不是再给卖家一个聊天机器人，而是一个能理解店铺、主动拆任务并持续推进的 AI CEO。它可以先读取官方店铺数据，生成和保存未发布草稿、整理素材和经营建议；涉及正式发布、退款、广告预算等风险动作时，一定交给商家确认。我们现在已经跑通真实 eBay、微信支付和运营后台，正在用首批真实卖家验证价值和打磨体验。

### 面向潜在客户的两分钟结构

1. **问题：**“你每天有多少时间花在整理商品、重复上架、查数据和来回切平台上？”
2. **定位：**“捷境不是 ERP，也不是只会回答问题的聊天机器人，而是 eBay-first 的 AI CEO 工作台。”
3. **工作方式：**“它读取官方店铺数据，把目标拆成任务，生成可执行成果并留下来源和记录；低风险步骤自动推进，高风险动作进入确认中心。”
4. **安全边界：**“令牌和密钥只在后端保管；发布、退款和预算不会被 AI 私自执行。”
5. **当前阶段：**“产品已经能真实运行和收费，现在是邀请制首批用户阶段；我们不夸大成熟度，会根据真实使用持续迭代。”
6. **邀请：**“如果你愿意，可以拿一个真实店铺和一个真实商品试一遍，看看它能否减少重复劳动并更快产出可用草稿。”

### 不建议说的话

- 不说“完全无人值守”——高风险动作必须有人确认。
- 不说“什么平台都支持”——当前核心是 eBay-first。
- 不说“AI 保证赚钱”——捷境提升执行效率和决策信息，不保证经营结果。
- 不说“已经是成熟大规模 SaaS”——现在是可收费的邀请制 MVP，市场验证仍为 0 订阅。
- 不强调底层 Hermes、Vault、CCN 等技术名词——客户关心的是少做重复工作、风险可控和结果可追踪。

## 十、最终判断

方向是对的，技术底座也已经跨过“能不能做出来”的阶段。现在最大的风险不是服务器小，也不是少一个 Redis，而是**公开信息、真实开关、运营队列和增长数据没有形成同一套可信事实**。

下一步应停止无边界加功能，先用第一阶段五项修复把“收费上线可信度”从 68 提升到 85 左右，然后邀请 5–10 个真实卖家完成从注册到首次价值、付款、售后的闭环。只有真实用户愿意持续使用，项目才算从“上线”走到“落地”。
